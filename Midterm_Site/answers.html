X1 · Ch1 Introduction

X1-01OS definition, intermediary, four componentsCH1

What is an operating system? Explain its role among the four components of a computer system. [1.20–1.21]

An OS is system software that acts as an intermediary between users / application programs and the computer hardware; it controls and coordinates the use of computing resources among various applications and users.

  • Four components: hardware (CPU, memory, I/O devices) → operating system → application programs (define how resources are used to solve problems, e.g., editors, browsers, games) → users (people, machines, other computers).
  • Abstraction: the OS hides the complicated details of the hardware and provides a simple, easy-to-use interface, so users deal with files, photos and web pages instead of bytes and blocks on devices.
  • Resource allocation: it gives an orderly and controlled allocation of processors, memory, disks and I/O devices among programs.
X1-02OS goals in different computing environmentsCH1

How do OS design goals differ for shared computers, workstations, mobile devices, embedded systems and real-time systems? [1.22]

The OS design first and foremost depends on the target device:

Environment Main OS goal / feature
Shared computers (mainframe, minicomputer) keep all users satisfied: balance performance vs. fairness
Individual systems (workstations) dedicated resources: performance rather than fairness; may use shared resources from servers
Mobile devices (smartphones, handhelds) resource constrained; sensors; touch screen and voice control (e.g., Siri); optimized for usability and battery life
Embedded systems (air conditioners, cars, ships, spacecraft) little or no user interface; OS pre-installed in ROM
Real-time systems strict time constraints
X1-03OS goals, resource allocator, control programCH1

What are the main goals of an OS? Explain the views of the OS as a resource allocator and as a control program. [1.23]

Two main goals: user convenience (an environment to execute programs in a convenient, safe, protected and efficient manner) and resource allocation (allocate resources fairly and efficiently).

  • Resource allocator: the OS manages all resources, hardware (CPU, memory, I/O) and software (e.g., signals, locks), and decides between conflicting requests for efficient and fair resource use.
  • Control program: the OS controls the execution of programs to prevent errors and improper use of the computer (stops users misusing resources; handles I/O).
  • In a nutshell, the OS manages and controls the hardware and helps programs run on the computer.
X1-04Scenario: which OS roleCH1

Which OS role does each case show? (a) Two programs request the only printer at the same time. (b) A program writing into another program's memory is stopped. (c) A user opens a photo by file name, not by disk block numbers. [1.21, 1.23]

  • (a) Resource allocator: the OS decides between conflicting requests (one job gets the printer, the other waits), so the device is shared fairly and efficiently.
  • (b) Control program: the OS controls program execution to prevent errors and improper use; each program may access only its own memory.
  • (c) Abstraction / user convenience: the OS hides hardware details (bytes and blocks) behind a simple interface (files).
X1-05Kernel, middleware, system and application programsCH1

Distinguish the kernel, middleware, system programs and application programs. Which of them are part of the OS? [1.23–1.24]

There is no universally accepted definition of an OS ("everything a vendor ships" is only an approximation); commonly, OS = always-running kernel + middleware frameworks + system programs.

Term Meaning Part of OS? Example
Kernel "the one program running at all times on the computer"; the essential functions yes process and memory management
Middleware software frameworks that provide additional services to application developers yes (popular in iOS, Android) databases, multimedia, graphics
System programs ship with the OS but are not part of the kernel; help manage the system while it runs yes shells, compilers, ls, cp
Application programs not associated with the OS no apps from app stores, games
X1-06Computer-system organization: bus, controllers, driversCH1

Describe the organization of a modern computer system. Why do the CPUs and devices compete for memory? [1.25, 1.27]

A computer has one or more CPU cores and device controllers connected through a common bus that provides access to shared memory.

  • CPUs and devices execute concurrently, so they compete for memory cycles through the shared bus (a memory controller keeps the access orderly).
  • Each device controller is in charge of a particular device; the OS controls it through a device driver (the kernel module that controls a device).
  • Basic I/O hardware elements: buses, device controllers and the devices themselves.
X1-07von Neumann architecture, stored-program conceptCH1

Describe the main components of the von Neumann architecture. What does "stored-program" mean? [1.26]

  • Processing unit (CPU): an arithmetic logic unit (ALU) and processor registers: PC (program counter), AC (accumulator), MAR (memory address register), MDR (memory data register).
  • Control unit: an instruction register (IR) and the program counter (PC).
  • Memory that stores both data and instructions (with caches), external mass storage (secondary storage), and input and output mechanisms.

Stored-program: instructions and data are stored in the same memory and accessed by address, so programs and data must be brought into memory before execution.

X1-08Instruction-execution cycle stepsCH1

Describe the steps of the instruction-execution cycle on a von Neumann machine. [1.26]

  1. Fetch instruction: the instruction at the address in the PC is fetched from memory (or cache) into the instruction register (IR).
  2. Decode instruction.
  3. Fetch data: the operands are fetched from memory (or cache) into data registers.
  4. Execute instruction: the ALU operates on the operands.
  5. Write back (if any): the result may be stored back in memory or cache.

The cycle then repeats for the next instruction.

X1-09Why programs must be in memory; MMUCH1

Why must a program be loaded into main memory before it can run? What does the memory management unit (MMU) "see"? [1.26, 1.30]

Because main memory is the only large storage the CPU can access directly; the CPU accesses secondary storage only indirectly, so code and data on disk must first be brought into memory.

  • In the von Neumann (stored-program) model, the CPU fetches every instruction and operand from memory (or cache / registers).
  • The MMU sees only a stream of memory addresses; it does not know how they are generated, or whether they are instructions or data.
X1-10I/O subsystem: buffering, caching, spooling, driversCH1

What services does the kernel I/O subsystem provide? Distinguish buffering, caching and spooling, and state what a device driver does. (Ch1 summary, Lab 2)

The kernel I/O subsystem provides I/O scheduling, buffering, caching, spooling, device reservation and error handling.

  • Buffering: stores data temporarily while it is being transferred (e.g., between a device and an application).
  • Caching: keeps a copy of data on faster storage. Difference: a buffer may hold the only existing copy of a data item, whereas a cache only holds a copy of an item that resides elsewhere.
  • Spooling: holds output for a device that cannot accept interleaved data (e.g., a printer), coordinating concurrent output.
  • Device driver: the kernel module that controls a device; it hides device details behind a uniform device-access interface for the I/O subsystem.
X1-11Storage units: bits, bytes, words, KB–PBCH1

(Calculation) A computer has 64-bit registers and addressing. (a) Bytes per word? (b) Words in 1 KB? (c) Bytes in 4 GB? (d) Time to send a 1 GB file over a 1 Gb/s link? [1.28]

Use 1 byte = 8 bits; KB = 210 = 1,024 bytes, MB = 10242, GB = 10243, TB = 10244, PB = 10245 bytes; a word is the architecture's native unit of data; networks are measured in bits per second (Mb/s, Gb/s).

  • (a) 64 bits / 8 = 8 bytes per word.
  • (b) 1,024 / 8 = 128 words.
  • (c) 4×230=232 = 4,294,967,296 bytes (manufacturers round this to about 4 billion).
  • (d) 230×8 = 8,589,934,592 bits; at 109 bits/s this takes about 8.6 s (about 8 s if 1 GB is rounded to 109 bytes). Always multiply bytes by 8 before dividing by a network rate.
X1-12Storage hierarchy: speed, cost, capacity, volatilityCH1

Describe the storage hierarchy. How do speed, cost, capacity and volatility change as we move down it? [1.29]

Storage is organized in a hierarchy by speed, cost per byte, capacity and volatility: registers → cache → main memory → nonvolatile memory (e.g., SSD) → hard-disk drives → optical disk → magnetic tapes.

  • Higher levels (closer to the CPU) are faster, smaller and more expensive per byte.
  • Moving down, cost per byte decreases, access time increases (slower) and capacity increases.
  • Registers, cache and main memory are volatile (primary storage); NVM and HDDs are nonvolatile (secondary storage); optical disks and tapes are tertiary storage.
X1-13Why secondary storage is neededCH1

Why can't all programs and data be kept permanently in main memory? What is secondary storage for? [1.30–1.31]

Because main memory is volatile (it loses its contents when power is turned off) and is too small and too costly per byte to hold all programs and data.

  • Secondary storage is an extension of main memory that provides large nonvolatile storage capacity, holding large quantities of data permanently.
  • The most common devices are hard-disk drives (HDDs) and nonvolatile memory (NVM) devices such as SSDs; programs are loaded from them into memory when they run.
X1-14Main memory properties, bootstrap in EEPROMCH1

Describe main memory. Where is the bootstrap program stored, and why not in main memory? [1.30]

  • Main memory is the only large storage the CPU can access directly; it is volatile, typically DRAM, accessed by load and store instructions to specific addresses, and byte addressable (each address refers to one byte).
  • The bootstrap program, the first program run at power-on, is stored in EEPROM (electrically erasable programmable read-only memory, i.e., firmware).
  • Reason: DRAM is volatile and empty at power-on, so start-up code must be in nonvolatile memory; the bootstrap program initializes the system and loads the OS kernel into memory.
X1-15Mechanical vs electrical (NVM) storageCH1

Compare mechanical and electrical secondary storage. [1.31]

Mechanical storage is larger and cheaper per byte; electrical storage (NVM) is more costly, smaller, more reliable and faster.

Mechanical Electrical (NVM)
Examples HDDs, optical disks, holographic storage, magnetic tape flash memory, SSD, FRAM, NRAM
Capacity larger smaller
Cost per byte less expensive more costly
Speed slower faster
Reliability lower (moving parts) more reliable

Both are nonvolatile and hold programs and data permanently.

X1-16Cache hit, miss, cache managementCH1

Explain what happens on a cache hit and on a cache miss. What are the main cache-management issues? [1.32]

Caching temporarily copies a subset of information from a slower, larger storage into a faster, smaller storage, making the frequently used case faster. Every access first checks whether the information is in the cache:

  • Hit: it is in the cache, so it is used directly from the cache (fast).
  • Miss: it is not, so the data is copied from the slower storage into the cache and used there.
  • Cache management: the cache is much smaller than the storage being cached, so the key issues are the cache size and the replacement policy (what to evict); the major criterion is the cache hit ratio (percentage of accesses found in the cache).
X1-17Where caching is used in systemsCH1

Caching is "performed at many levels". Give examples of caching in a computer system or OS. [1.32]

Caching is used whenever a subset of content can be kept on a faster device:

  • Hardware caches keep recently used parts of main memory close to the CPU.
  • Recent address translations are cached for fast lookup.
  • File blocks, file names and file directories: e.g., part of the file directory (a kernel data structure stored on disk) is cached in main memory, so main memory acts as a cache for the disk.
  • Frequently used network routes are cached.
X1-18Average access time; miss time vs penaltyCH1

(Calculation) Hit ratio 98%, hit time 1 ns, miss time 60 ns: find the average access time. What if 60 ns is the miss penalty instead? [1.32]

Average access time = (hit ratio × hit time) + (miss ratio × miss time), where miss ratio = 1 − hit ratio: Tavg​=h×Thit​+(1−h)×Tmiss​

  • Miss time 60 ns: Tavg​=0.98×1+0.02×60=0.98+1.2= 2.18 ns.
  • If 60 ns is the miss penalty (extra time on top of the hit time), then Tmiss​=1+60=61 ns and Tavg​=0.98×1+0.02×61=0.98+1.22= 2.20 ns (same as Thit​+(1−h)×penalty=1+0.02×60).

State which interpretation you use.

X1-19Higher hit ratio is not always betterCH1

(Calculation) Cache A: hit ratio 95%, hit time 4 ns, miss time 100 ns. Cache B: hit ratio 90%, hit time 1 ns, miss time 60 ns. Which is better, and what does this show? [1.32]

Cache B is better, even though its hit ratio is lower.

  • Formula: Tavg​=h×Thit​+(1−h)×Tmiss​.
  • A: 0.95×4+0.05×100=3.8+5= 8.8 ns.
  • B: 0.90×1+0.10×60=0.9+6= 6.9 ns.
  • This shows that hit ratio alone does not determine cache performance: the average access time also depends on the hit time and the miss time (miss penalty).
X1-20Required hit ratio and caching speedupCH1

(Calculation) Hit time 2 ns, miss time 82 ns, and an access without the cache takes 80 ns. What hit ratio gives an average access time of at most 6 ns? What is the speedup over no cache? [1.32]

A hit ratio of at least 95% is needed, giving a speedup of about 13.3 times.

  • h×2+(1−h)×82≤6⇒82−80h≤6⇒80h≥76⇒h≥0.95.
  • General form: h=(Tmiss​−Ttarget​)/(Tmiss​−Thit​) = (82 − 6) / (82 − 2) = 76 / 80 = 0.95.
  • Check: 0.95×2+0.05×82=1.9+4.1=6 ns; speedup = 80 / 6 ≈ 13.3 compared with accessing memory directly.
X1-21Locality: temporal, spatial, when caching failsCH1

Why does caching work? Identify the temporal and spatial locality in a loop that sums an array. When would a cache not help? [1.33]

Caching works because programs show locality of reference:

for (i = 0; i < n; i++)
    sum += a[i];
  • Temporal locality (locality in time): recently accessed items are likely to be accessed again soon; here sum, i and the loop instructions are reused in every iteration.
  • Spatial locality (locality in space): items near recently accessed items are likely to be accessed shortly; a[0], a[1], a[2], ... are contiguous and accessed in order (instructions are also sequential), so one block brought into the cache serves the next accesses.
  • Without locality, e.g., if all items are accessed with equal probability, the cache would never work: the hit ratio stays low and most accesses pay the miss time.
X1-22Who manages each storage levelCH1

Which component manages each level of the storage hierarchy? Is movement between levels explicit or implicit? [1.34]

Registers are managed by the compiler, the cache by hardware, and main memory, SSD and disk by the OS.

Level Access time (ns) Managed by Backed by
Registers 0.25–0.5 compiler cache
Cache 0.5–25 hardware main memory
Main memory 80–250 operating system disk
Solid-state disk 25,000–50,000 operating system disk
Magnetic disk 5,000,000 operating system disk or tape

Movement between levels can be explicit or implicit: cache ↔ memory transfers are implicit (done by hardware), while memory ↔ disk transfers (e.g., loading a program, swapping) are explicitly controlled by the OS.

X1-23Timescales: why switch jobs during disk I/OCH1

Using typical latencies, explain why the OS should run another job while one job waits for a disk access. [1.35, 1.42]

A disk access is about 100,000 times slower than a memory access, so a waiting CPU would waste millions of instruction times.

  • Main memory reference ≈ 100 ns; disk seek ≈ 10 ms = 107 ns, so 107/102=105 times slower (an L1 cache reference is only ≈ 0.5 ns).
  • Therefore, under multiprogramming, when the running job waits for I/O the OS switches the CPU to another job, so the CPU always has a job to execute.
X1-24Single-processor system, special-purpose processorsCH1

A PC has one single-core CPU plus a disk controller and a GPU that contain their own processors. Is it a multiprocessor system? Explain. [1.36]

No, it is still a single-processor system. It has one general-purpose CPU with a single processing core, which executes a general-purpose instruction set, including user processes.

  • The disk controller and GPU are special-purpose (device-specific) processors: they run a specific and limited instruction set and usually do not execute instructions from user processes.
X1-25Multiprocessor advantages; speed-up below NCH1

Give three advantages of multiprocessor systems. Why is the speed-up with N processors less than N? What is the main disadvantage? [1.37]

  • Increased throughput: more computing capability, so more work is done in less time.
  • Economy of scale: processors share I/O devices, power supplies, housings and peripherals, so it costs less than several single-processor systems.
  • Increased reliability: graceful degradation (service continues in proportion to the surviving hardware) or fault tolerance (operation continues despite a component failure).

Speed-up is less than N because of overhead, e.g., contention for shared resources (bus or memory) and coordination among processors. Disadvantage: far more complex hardware design and software (parallel programming).

X1-26SMP vs AMP comparisonCH1

Compare symmetric multiprocessing (SMP) and asymmetric multiprocessing (AMP). [1.37–1.38]

In AMP a master processor assigns tasks to slaves and handles I/O; in SMP all processors are equal and each performs all tasks.

Asymmetric (AMP) Symmetric (SMP)
Relationship master–slave: the master assigns specific tasks to the slaves all processors treated equally
OS functions and user processes run as the master assigns each processor performs all tasks, including OS functions and user processes
I/O handled by the master only handled by any processor
Weakness the master can become a bottleneck adding CPUs may not scale: contention for the system bus

In SMP, each CPU has its own set of registers and a private (local) cache, but all processors share physical memory through the system bus.

X1-27Cache coherency with private cachesCH1

In an SMP system each CPU has its own private cache. What problem does this create, and who usually solves it? [1.38]

Cache coherency: the same data item can be copied in several CPUs' private caches, so after one CPU updates its copy, the other caches may hold stale values.

  • The system must ensure that an update in one cache is immediately reflected in all other caches holding that item, so every CPU reads the most recent value.
  • This is usually handled by hardware, below the OS level.
X1-28Multicore benefits for laptops and mobile devicesCH1

Why is one multicore chip preferred to several single-core chips, especially in laptops and mobile devices? [1.39]

  • Faster communication: cores on one chip communicate on-chip, which is faster than between-chip communication.
  • Lower power: one chip with multiple cores uses significantly less power than multiple single-core chips, which matters for battery-powered devices such as mobile devices and laptops.
X1-29NUMA: motivation, structure, drawbackCH1

Why was NUMA introduced? Describe its structure, its drawback and its implication for the OS. [1.40]

  • Motivation: adding more CPUs to an SMP system may not scale, because contention for the system bus becomes a bottleneck.
  • Structure: each CPU (or group of CPUs) has its own local memory accessed via a small, fast local bus; the CPUs are connected by a shared system interconnect, and all CPUs share one physical memory address space. Local memory is fast, remote memory is slower (non-uniform access time).
  • Drawback: increased latency when a CPU must access remote memory across the system interconnect.
  • OS implication: scheduling and memory management should keep a process on a CPU close to the memory that holds its data.
X1-30CPU, processor, core, multicore, multiprocessorCH1

Define CPU, processor, core, multicore and multiprocessor. [1.41]

A processor (chip) contains one or more CPUs, and the core is the unit that actually executes instructions:

Term Definition
CPU the hardware that executes instructions
Processor a physical chip that contains one or more CPUs
Core the basic computation unit of the CPU; it executes instructions and has registers for storing data locally
Multicore multiple computing cores on a single physical processor chip
Multiprocessor a system including multiple processors
X1-31Multiprogramming: why, how, OS supportCH1

Why is multiprogramming needed? What happens when the running job waits for I/O, and what OS support does it need? [1.42]

A single program cannot keep the CPU or I/O devices busy at all times, so multiprogramming keeps several jobs in memory at the same time and organizes them so the CPU always has one to execute, raising CPU utilization (efficiency).

  • When the running job waits for I/O, the OS switches the CPU to another job in memory instead of leaving the CPU idle.
  • OS support: job scheduling (choose queued jobs to load into memory), CPU scheduling (several jobs ready at the same time), memory management for several jobs, swapping (move processes in and out of memory when they do not fit) and virtual memory (run a process that is not completely in memory).
X1-32Multiprogramming vs time sharing comparedCH1

Compare multiprogramming (batch) and time sharing (multitasking). [1.42]

Time sharing is a logical extension of multiprogramming: both keep several jobs in memory, but time sharing switches the CPU so often that users can interact with their programs.

Multiprogramming (batch) Time sharing (multitasking)
Goal efficiency: keep the CPU busy (CPU utilization) fast response time for interactive users
When the CPU switches when the running job must wait (e.g., for I/O) frequently, even if the job is not waiting (short time slices, enforced by a timer)
User interaction none while jobs run (jobs are submitted and queued) users interact with each job while it is running (interactive computing)
Requirement job scheduling, CPU scheduling CPU scheduling; response time under a certain threshold
X1-33Virtualization: host, VMM, guest OSCH1

What is virtualization? Describe the roles of the host, the VMM (hypervisor) and the guest OS. [1.43–1.44]

Virtualization abstracts the hardware of a single computer into multiple different execution environments (virtual machines, VMs), creating the illusion that each user or program runs on its own "private computer". It allows an OS to run as an application within another OS, so one physical machine can run multiple operating systems concurrently.

  • Host: the underlying hardware system.
  • Virtual machine manager (VMM) or hypervisor: creates and manages virtual machines by providing an interface identical to the host; it is in complete control of system resources.
  • Guest: a process given a virtual copy of the host, usually an operating system (guest OS) running its own applications.
X1-34Virtualization motivations: consolidation, testing scenarioCH1

A company runs many lightly loaded servers, each needing a different OS or OS version, and its developers must test software on several OSes. How does virtualization help? [1.43]

  • Server consolidation: virtualization consolidates multiple OSes onto fewer hardware platforms; each service runs in its own VM with the OS / version it needs, on far fewer physical machines.
  • Testing and debugging: developers can run many OS types and versions on just one machine, which makes testing and debugging easier.
  • Desktop use: a user can run one OS (e.g., Linux) and still use native applications of another platform, such as Windows, inside a VM.
X1-35Virtualization vs emulation; VM performanceCH1

Distinguish virtualization from emulation. Does a program run faster inside a VM? [1.46]

  • Virtualization: the guest OS is natively compiled for the same CPU as the host; most guest instructions run directly on the hardware under VMM control, so programs show only minor performance decreases (they pass through more layers of software).
  • Emulation: simulates a different CPU architecture in software (source CPU differs from target CPU); every instruction must be translated, so it is much slower.
  • So a program in a VM is not faster than on the physical machine; it is usually slightly slower. (History: virtualization began on IBM mainframes (1972); in the late 1990s Intel CPUs became fast enough for VMware and Xen on PCs.)
X1-36Cloud computing; public, private, hybrid cloudsCH1

What is cloud computing, and why is it a "logical extension of virtualization"? Distinguish public, private and hybrid clouds. [1.47–1.48]

Cloud computing delivers computing, storage and applications as a service over a network, on demand.

  • It is a logical extension of virtualization because it uses virtualization as the base for its functionality; e.g., Amazon EC2 has millions of servers running tens of millions of VMs, and users pay based on usage.
  • Public cloud: available via the Internet to anyone willing to pay.
  • Private cloud: run by a company for the company's own use.
  • Hybrid cloud: includes both public and private cloud components.
X1-37SaaS, PaaS, IaaS classificationCH1

Explain SaaS, PaaS and IaaS, and classify: (a) an online word processor; (b) a ready-to-use database server for your application; (c) rented storage for backups or virtual servers. [1.48]

SaaS provides applications, PaaS a ready software stack, and IaaS servers or storage, all over the Internet.

Model Provided over the Internet Example
SaaS (Software as a Service) one or more applications (a) online word processor
PaaS (Platform as a Service) a software stack ready for application use (b) a database server

X2 · Ch2 OS Structures

X2-01OS services: helpful to user, efficient operationCH2

List the OS services that are helpful to the user, and those that ensure the efficient operation of the system itself. [2.4–2.6]

Helpful to the user:

  • User interface: CLI, GUI, touch screen.
  • Program execution: load a program into memory, run it, and end execution normally or abnormally (indicating error).
  • I/O operations: a running program may require I/O on a file or an I/O device.
  • File-system manipulation: read, write, create, delete and search files and directories; list file information; permission management.
  • Communications: processes exchange information on the same computer or over a network, via shared memory or message passing (packets moved by the OS).
  • Error detection: errors may occur in the CPU and memory, in I/O devices and in user programs; the OS takes appropriate action to ensure correct and consistent computing (plus debugging facilities).

Efficient operation of the system (via resource sharing): resource allocation (CPU cycles, memory, file storage, I/O devices), logging (keep track of which users use how much and what kinds of resources), and protection and security.

X2-03Protection vs security; access rights, domainsCH2

Distinguish protection and security. What are an access right and a domain? [2.6] (Ch2 summary)

  • Protection: controlling the access of users or processes to the resources (hardware and software) of the computer, ensuring that all access to system resources is controlled, so concurrent processes do not interfere with each other.
  • Security: defending the system against internal and external attacks (e.g., denial-of-service, worms, viruses); security from outsiders requires user authentication and extends to defending external I/O devices from invalid access attempts.
  • An access right is the permission to perform certain operations on an object; a domain is a set of access rights for a set of objects. A process executes in a domain and cannot perform an operation on an object unless its domain allows it.

X2-06Shell: functions; kernel or system programCH2

A shell (1) fetches a command from the user, (2) interprets it and (3) executes it; in UNIX it runs a program by calling fork() to create a new process and exec() to load the program into it, then waits for it (or continues, for a background job).

The command interpreter is sometimes implemented in the kernel, sometimes by system programs. As a system program:

  • Several shells can coexist (C shell, Bourne-Again shell, Korn shell), and users can choose or replace one without changing the kernel.
  • Most commands are separate system programs: the shell just uses the command name to find a file to load and execute, so new commands can be added without modifying the shell.
  • A bug in the shell affects only the shell process, not the kernel.
X2-07cp command: sequence of system callsCH2

Describe the sequence of system calls needed by cp in.txt out.txt to copy one file to another. [2.14]

Even this simple command needs a sequence of system calls:

  1. Acquire the input and output file names (from the command line, or by writing a prompt to the screen and reading the keyboard).
  2. Open the input file; if it does not exist, print an error and abort.
  3. Create the output file; if it already exists, abort (or overwrite).
  4. Loop: read from the input file and write to the output file, until the read reaches end of file (or an error occurs).
  5. Close the files, write a completion message to the screen, and terminate normally.
X2-08API definition, common APIs, read() exampleCH2

What is an API? Name the three most common APIs, and explain the parameters and return value of ssize_t read(int fd, void *buf, size_t count). [2.15–2.16]

An Application Programming Interface (API) specifies a set of functions available to application programmers, including the parameters passed to each function and the return values it may expect. The API functions invoke the actual system calls on behalf of the programmer (e.g., Windows CreateProcess() invokes the NTCreateProcess() system call). Programmers use an API through a library provided by the OS: libc for C programs on UNIX/Linux.

  • Most common APIs: Win32 API (Windows), POSIX API (virtually all versions of UNIX, Linux and Mac OS X), Java API (Java virtual machine).
  • read(): fd = the file descriptor to be read; buf = the buffer the data is read into; count = the maximum number of bytes to read. It returns the number of bytes read, 0 at end of file, and −1 if an error occurred.
X2-09Why use APIs; API call vs system callCH2

Explain why programmers use an API rather than invoking system calls directly. Does every API call result in a system call? [2.17]

  • Program portability: a program written to an API can compile and run on any system that supports the same API, although the implementation of system calls varies from machine to machine.
  • Hiding complex details: actual system calls are more detailed and difficult to work with; the caller need know nothing about how the system call is implemented, only obey the API and understand what the OS will do as a result. E.g., printf() handles formatting and buffering, then calls the write() system call.
  • No: an API function may invoke one or more system calls, or none; e.g., strlen() runs entirely in user mode.
X2-10System-call interface, RTE, system-call tableCH2

How does the system-call interface link an API call to the kernel? Explain the roles of the run-time environment, the system-call number and the system-call table. [2.18–2.19]

The system-call interface, part of the run-time environment, maps each API call to a numbered system call and invokes it in the kernel.

  • The run-time environment (RTE), the full suite of software needed to run programs in a language (compilers or interpreters, libraries, loaders), provides a system-call interface that serves as the link to the system calls of the OS.
  • An identity number is associated with each system call, and the system-call interface maintains a table indexed by these numbers.
  • The interface intercepts function calls in the API, invokes the necessary system call within the OS (the call traps into kernel mode; the kernel uses the number to index the table and run the service routine), and returns the status of the system call and any return values.
  • The caller knows nothing about how the system call is implemented.
X2-11printf() vs write(); when kernel mode startsCH2

Explain the relationship between printf() and write(). At what point does the program enter kernel mode? [2.26]

printf() is a standard C library (API) function; write() is a system call. The program invokes the printf() library call, which calls the write() system call to get the service from the OS.

  • printf() runs in user mode (formatting the string and buffering the output).
  • Only when the library invokes write() does the program trap into kernel mode; the kernel writes the data to the file or device and then returns to user mode with the result.
  • The standard C library (libc) thus provides the system-call interface for UNIX and Linux.

X2-16Compiler, linker, loader roles; relocationCH2

What does each of the compiler, linker and loader do? What is a relocatable object file, and what is relocation? [2.31–2.32]

The compiler produces relocatable object files, the linker combines them into one executable on disk, and the loader brings that executable into memory to run.

gcc -c main.c            # compiler -> main.o (relocatable object file)
gcc -o main main.o -lm   # linker   -> main (executable; -lm links the math library)
./main                   # loader   -> program loaded into memory (+ DLLs if needed)
  • A relocatable object file is compiled code designed to be loaded into any physical memory location.
  • Linker: combines the relocatable object files, along with libraries if needed, into a single binary executable file stored on secondary storage.
  • Loader: brings the binary executable into memory, possibly with dynamically linked libraries, where it becomes eligible to run on an available CPU.
  • Relocation assigns final addresses to the program parts and adjusts the code and data to match those addresses. Object and executable files have standard formats (machine code + symbol table, e.g., ELF on Linux), so the OS knows how to load and start them.

X2-18Why applications are OS-specific; ABICH2

Why can an executable built for one OS usually not run on another OS? How can programs be made portable? [2.15, 2.31, 2.56]

Because each OS has its own system calls, executable format and binary conventions.

  • Different system calls / APIs: each OS provides its own set of system calls (different numbers, parameters, meanings and results), e.g., Win32 vs POSIX.
  • Different executable formats: each OS uses its own standard binary format so it knows how to load and start the program (e.g., ELF on Linux, PE on Windows).
  • Different CPUs have different instruction sets: e.g., iOS runs on ARM and does not run Mac OS X (Intel) applications natively. The rules for how binary code interfaces with a given OS on a given architecture are called the ABI (application binary interface).

Portability: write to a standard API (e.g., POSIX) and recompile on each system, or use an interpreted or virtual-machine language such as Java (JVM).

X2-19OS design goals: user vs systemCH2

What are user goals and system goals in OS design? What affects the design at the highest level? [2.33]

  • At the highest level, the design is affected by the choice of hardware and the type of system (desktop/laptop, mobile, distributed or real-time); it starts by defining goals and specifications.
  • User goals: the OS should be convenient to use, easy to learn and use, reliable, safe and fast.
  • System goals (for designers and maintainers): it should be easy to design, implement and maintain, and flexible, reliable, error-free and efficient.
  • OS design is not "solvable"; it is a highly creative software-engineering task, though some approaches have proven successful.
X2-20Policy vs mechanism: definition, separationCH2

Distinguish policy and mechanism with an example. Why should they be separated? [2.34]

Policy: what will be done. Mechanism: how to do it.

  • Example: a timer is a mechanism for ensuring CPU protection, but deciding how long the timer is set for a particular user is a policy decision.
  • Why separate: policies change over time; if policy and mechanism are properly separated, a policy change needs minimal change to the mechanism, which gives flexibility. The same mechanism can support "I/O-intensive programs have priority over CPU-intensive ones" or the opposite policy.
  • In a nutshell, design goals determine the policies, and the OS implements these policies through specific mechanisms.

X2-22OS in a high-level language: pros, consCH2

What are the advantages and disadvantages of implementing an OS in a high-level language (C/C++) rather than assembly? [2.35]

The advantages outweigh the small costs, so most OSes are now written in C or C++ (the lowest levels of the kernel may still be in assembly; e.g., Android's system libraries are in C/C++ and its application frameworks mostly in Java).

X2-24Simple structure: why MS-DOS was vulnerableCH2

Why was MS-DOS vulnerable to buggy or malicious programs? [2.39]

Because nothing protected the OS and hardware from application programs.

  • MS-DOS has a simple structure: it was written to provide the most functionality in the least space, was not carefully divided into modules, and its interfaces and levels of functionality are not well separated.
  • Application programs can access I/O directly, bypassing the OS.
  • It was written for the Intel 8088, which had no dual mode (kernel vs. user mode) and no hardware protection, so one faulty program could crash the whole system.
X2-25Monolithic kernel: pros, cons, LinuxCH2

What is a monolithic kernel? Why do UNIX, Linux and Windows still use this structure despite its drawbacks? [2.40–2.42]

A monolithic structure places all the functionality of the kernel into a single, static binary file that runs in a single address space; in traditional UNIX, the kernel is everything below the system-call interface and above the physical hardware (UNIX = kernel + system programs).

  • Why still used: a distinct performance advantage, since there is very little overhead in the system-call interface, and communication within the kernel is fast.
  • Drawback: an enormous amount of functionality is combined into one level, making it difficult to implement, debug and maintain; it is tightly coupled.
  • Linux is monolithic (it runs entirely in kernel mode in a single address space; applications use glibc to reach the system-call interface) but also modular: loadable kernel modules let the kernel be modified at run time.
X2-26Tightly vs loosely coupled; modular designCH2

Distinguish a tightly coupled system from a loosely coupled (modular) one. What is the advantage of modularity? [2.43]

  • Tightly coupled (monolithic): essentially one big program running in one address space, where changes to one part of the system affect other parts.
  • Loosely coupled (modular): the system is divided into separate, smaller components, each with specific and limited functionality, with specified interactions between them.
  • Advantage: changes in one component affect only that component, giving more freedom and flexibility in creating and modifying each component and simplifying debugging and verification. The layered approach is one way to make a system modular.
X2-27Layered approach: information hiding, debuggingCH2

Describe the layered approach. What is information hiding, and why is a layered OS easy to construct and debug? [2.44–2.45]

The OS is divided into layers, each built on top of lower layers: layer 0 (bottom) is the hardware; layer N (top) is the user interface. Each layer has data structures and a set of functions, uses the services of the layer below and offers services to the layer above.

  • Information hiding: a layer needs to know only what the lower-layer operations do (their interface), not how they are implemented; each layer hides its own data structures, operations and hardware from higher layers.
  • Main advantage, simplicity of construction and debugging: layers are debugged one at a time, starting from the lowest layer; when a layer is tested, the layers below are already verified, so an error found must be in the layer being tested.
  • Layering is used successfully in other systems such as computer networks (TCP/IP) and web applications.
X2-28Why few OSes are purely layeredCH2

Why do few operating systems use a pure layered approach? What is the trend instead? [2.45, 2.53]

  1. Difficulty of defining the layers: there are significant challenges in appropriately defining the layers and their functionalities, since each layer may use only lower layers.
  2. Performance: the overhead of requiring a program to traverse multiple layers to obtain a service.

Trend: fewer layers with more functionality and modularized code, avoiding the problems of complex layer definition and interaction.

X2-29Microkernel: file access by message passingCH2

In a microkernel OS, describe how an application reads a file. Why does this hurt performance? [2.46–2.47]

The application and the file server never interact directly; they exchange messages through the microkernel.

  • The microkernel keeps only minimal process and memory management plus a communication facility (IPC); services such as the file server and device drivers run as user-level programs in separate address spaces.
  • To read a file, the application sends a request message to the microkernel, which passes it to the file server; the file server does the work and replies by message through the microkernel.
  • Performance cost: each request needs several user-to-kernel transitions and message copies between separate address spaces (increased system-function overhead), instead of one function call inside a monolithic kernel.
X2-30Microkernel: advantages, drawback, Windows NTCH2

Why is a microkernel OS easier to extend and port, and more secure and reliable? What is its main drawback? Give an example. [2.48]

  • Easier to extend: new services are added in user space without modifying the kernel; when the kernel must change, the changes are fewer because the kernel is much smaller.
  • Easier to port: the much smaller kernel can be more easily ported from one hardware platform to another.
  • More secure and reliable: less code runs in kernel mode; most services run as user processes, so if a service fails, the rest of the OS remains untouched; a simpler kernel is also more reliable.
  • Main drawback: performance suffers from increased system-function overhead: user-space to kernel-space communication and copying messages between services in separate address spaces. Example: Windows NT (a layered microkernel) performed worse than Windows 95, so Windows XP became more monolithic.
X2-31LKM approach; USB device scenarioCH2

What is the loadable kernel module (LKM) approach? What happens when a USB device is plugged into a running Linux machine whose kernel lacks its driver? [2.49–2.51]

The kernel has a set of core components and links in additional services via modules, either at boot time or during run time; this is the best current methodology in OS design.

  • USB case: the needed driver module is loaded dynamically into the running kernel (and can be removed later), with no need to recompile the kernel or reboot.
  • Why better: linking services dynamically is preferable to adding features directly to the kernel, which would require recompiling the entire kernel every time a change is made; since it is hard to predict every needed feature, functionality can be added and removed while the kernel is running.
  • Linux uses LKMs mainly for device drivers and file systems (Solaris also loads scheduling classes, loadable system calls, executable formats and STREAMS modules); the result is a dynamic, modular kernel with the performance benefits of a monolithic system.
X2-32LKM vs microkernel; LKM vs layeredCH2

Compare the LKM approach with the microkernel approach (one similarity, one difference). How does LKM also resemble a layered design? [2.50]

  • Similarity with a microkernel: the primary module has only core functions and knowledge of how to load and communicate with other modules; other services are added separately.
  • Difference: LKM is more efficient, because modules do not need to invoke message passing to communicate; they run inside the kernel and call each other directly, whereas microkernel services run in user space and talk through message passing.
  • Versus layered: like a layered design, each kernel section has a well-defined, protected interface, but LKM is more flexible, since any module can call any other module.
X2-33Hybrid systems: Linux, Windows, macOSCH2

Very few OSes adopt a single, strictly defined structure; they combine different structures to address performance, security and usability needs.

  • Linux: monolithic (OS in a single address space, so efficient performance) and modular (new functionality is dynamically added via LKMs).
  • Windows: largely monolithic, but keeps microkernel-like behaviour with separate subsystems (personalities) running as user-mode processes, and supports dynamically loadable kernel modules.
  • macOS / iOS: layered (user interface, application environments, kernel environment) with the kernel Darwin = Mach microkernel + BSD UNIX kernel, plus dynamically loadable kernel extensions (kexts).

X2-36Mac OS X structure: Darwin, Mach, BSDCH2

  • Mach provides fundamental OS services: memory management, CPU scheduling and IPC facilities.
  • BSD provides the POSIX API, networking, file system and security.
  • The kernel environment also has an I/O Kit for device drivers and dynamically loadable modules called kernel extensions (kexts).

Explain the roles of ART, JNI, HAL and Bionic in the Android architecture. [2.58–2.59]

  • ART (Android RunTime): the virtual machine on which Java applications execute, optimized for mobile devices with limited memory and CPU processing capabilities.
  • JNI (Java Native Interface): lets developers bypass the virtual machine and write Java programs that access specific hardware features; such programs are generally not portable from one hardware to another.
  • HAL (hardware abstraction layer): abstracts all hardware (camera, GPS chip, other sensors) and gives applications a consistent view independent of specific hardware.
  • Bionic: Google's standard C library for Android, used instead of glibc. Underneath is a modified Linux kernel for mobile systems (e.g., power management); libraries include WebKit, SQLite and SSL.
X2-40History: from batch to time sharingCH2

Briefly describe how operating systems evolved, and why the focus moved from hardware utilization to user convenience. [2.60]

Early on, hardware was expensive and humans relatively cheap, so OSes maximized hardware utilization; later hardware became cheap and humans expensive, so OSes focused on users.

  • Hand-programmed machines (1945–1955) had low hardware utilization, followed by batch processing (1955–1965) and multiprogramming (1965–1980): multiple jobs in memory, multiplexed over the CPU(s).
  • Time sharing: users share servers through cheap terminals. Personal computers: utilization is not a major concern; the focus is on user interfaces and APIs. Distributed OSes: consistency, performance, reliability and resource management. Real-time OSes: guarantee or prioritize jobs.

X3-01Program vs process; loading a programCH3

What is the difference between a program and a process? When does a program become a process, and can one program be associated with several processes?

  • A program is a passive entity — an executable file stored on disk. A process is an active entity — a program in execution, with a program counter specifying the next instruction to fetch and execute and a set of associated resources (address space, registers, open files).
  • A program becomes a process when its executable file is loaded into main memory (double-click an icon or enter a command in the shell): the OS (1) loads the code and static data, (2) allocates the run-time stack and fills in argc/argv, (3) allocates the heap, (4) sets up I/O — three open file descriptors: stdin (0), stdout (1), stderr (2).
  • Yes — one program can be executed by multiple processes (e.g., several copies of a web browser): the text section is the same, but each has its own data, heap, stack and PC, so they are separate execution sequences. A process can itself be an execution environment for other programs (e.g., the JVM).

X3-04PCB contents; process table; Linux task_structCH3

What is a Process Control Block (PCB) and what does it contain? How does the OS keep track of all PCBs, e.g., in Linux?

The PCB (task control block) is a kernel data structure holding all information associated with a process:

  1. Process state — new, ready, running, waiting, …
  2. Program counter — location of the next instruction to execute
  3. CPU registers — accumulators, index registers, stack pointers, general-purpose registers, condition codes
  4. CPU-scheduling information — priority, pointers to scheduling queues, scheduling parameters
  5. Memory-management information — memory allocated (page / segment tables)
  6. Accounting information — CPU time used, clock time elapsed, time limits
  7. I/O status information — I/O devices allocated, list of open files
  • Each process has a unique PID (positive integer; PID 1 = init / systemd). The process table (process list), indexed by PID, points to every PCB. Linux keeps a circular doubly linked list (task list) of struct task_struct (pid, state, time_slice, parent, children, files, mm).
  • The PCB is what is saved and restored in a context switch.
X3-05Threads within a processCH3

How is a thread represented, and what do the threads of one process share? Why use several threads in a process?

  • A thread is a single unique execution context: its own program counter, registers, execution flags and stack. It is executing when this context is resident in the CPU registers.
  • Threads of a process run within the same address space — they share code, data and open files, while each keeps its own thread state.
  • So a process can perform more than one task at a time (e.g., a web browser with one thread displaying images or text and another retrieving data from the network), and on multicore systems its threads run in parallel. A traditional single-threaded process is a heavy-weight process.
X3-06I/O-bound vs CPU-bound; good process mixCH3

Define I/O-bound and CPU-bound processes. Why should the long-term scheduler select a good process mix?

  • I/O-bound — spends more time doing I/O than computation; many short CPU bursts. CPU-bound — generates I/O requests infrequently, mostly computing; few very long CPU bursts.
  • A good mix keeps both the CPU and the I/O devices busy. If all processes are I/O-bound, the ready queue is almost always empty and the CPU idles; if all are CPU-bound, the I/O wait queues are almost always empty and the devices sit unused.
  • Hence the long-term scheduler (mainframes) strives for a good process mix to maximize CPU utilization.
X3-07Scheduling queues and the queueing diagramCH3

Which scheduling queues does the OS maintain, and how does a process migrate among them during its lifetime?

  • Ready queue — processes in main memory, ready and waiting to execute. Wait queues — processes waiting for an event such as I/O completion (one per device or event). The queues link PCBs (the PCB holds pointers to scheduling queues).
  • A new process joins the ready queue until it is dispatched. While running, it leaves the CPU when it:
    1. issues an I/O request → I/O wait queue → back to ready when the I/O completes;
    2. uses up its time slice → straight back to the ready queue;
    3. creates a child and waits for its termination → wait queue until the child ends;
    4. waits for an interrupt → wait queue until the interrupt occurs.
  • This repeats until it terminates. The state of a process is determined by the queue it is in (the running process is the exception), and each queue can have its own scheduling policy.

X3-09Swapping and the medium-term schedulerCH3

What is swapping? When and why does the medium-term scheduler swap a process out?

  • Swapping: the medium-term scheduler removes a partially executed process from memory, stores it temporarily on secondary storage (swap space), and later brings it back into memory to continue execution where it left off.
  • When: the degree of multiprogramming must be reduced — memory is over-committed / the workload is heavy and execution becomes slow (or to improve the process mix).

X3-10Context switch: saved state and kernel actionsCH3

What is a context switch? Describe the actions the kernel takes, and name events that cause one.

  • A context switch occurs when the CPU switches from one process (or thread) to another: the OS must save the state of the old process and load the saved state of the new process. The context is represented in the PCB — CPU registers, program counter, stack pointer, process state, memory-management information.
  • Kernel actions: (1) an interrupt or system call enters the kernel; (2) save the running process's context in its PCB, set its state (ready / waiting) and queue it; (3) the short-term scheduler selects the next process; (4) restore that process's context from its PCB and resume it in user mode. Architecture-specific work such as flushing data and instruction caches may also be needed.
  • Causes: timer interrupt (time slice expired); a system call that blocks (I/O request, wait()) or lets the scheduler pick another process (e.g., fork()); an interrupt that readies a higher-priority process; process termination.
X3-11Context-switch overhead; multiple register setsCH3

Why is context-switch time overhead, and what does it depend on? Some CPUs have multiple register sets: what happens if the new context is already in a register set, and if it is not?

  • Context-switch time is pure overhead — the system does no useful work while switching; the more complex the OS and the PCB, the longer the switch.
  • It is highly dependent on the hardware: memory speed, the number of registers to copy, and special instructions (e.g., a single instruction to load or store all registers).
  • Multiple register sets (e.g., SUN UltraSPARC): if the new context is already loaded, the switch only changes the pointer to the current register set — very fast. If it is in memory and all register sets are in use, one set must be saved to memory and the new context loaded from memory into it — slower, like an ordinary switch.
X3-12Context switch vs mode switchCH3

Is a context switch the same as switching from user mode to kernel mode? Explain.

No.

  • A mode switch flips the mode bit (user ↔ kernel) on a system call, interrupt or trap; the CPU saves the running process's state, runs kernel code and may return to the same process — e.g., getpid() returns at once and no other process runs.
  • A context switch changes which process runs: the kernel saves the old process's state in its PCB and loads another process's saved state. It is performed by the kernel (in kernel mode), typically after a timer interrupt or a blocking system call.
  • So every context switch requires entering the kernel, but a mode switch does not always lead to a context switch.
X3-13Interrupt-driven I/O and device controllersCH3

Explain how the CPU and a device controller cooperate to perform interrupt-driven I/O.

  • I/O devices and the CPU execute concurrently and asynchronously. Each device controller is in charge of a particular device and has a local buffer.
  • The device driver starts the operation by loading the controller's registers; the controller moves data between the device and its local buffer while the CPU continues other work.
  • When finished, the device controller informs the CPU by causing an interrupt (signal on the interrupt-request line): for input, data is available in the local buffer; for output, the I/O operation is completed.
  • The CPU handles the interrupt — for slow devices (keyboard, mouse) the CPU moves the data between the local buffer and main memory — and then returns to the interrupted instruction.
X3-14Interrupt handling and the interrupt vectorCH3

What is an interrupt? Describe how the CPU handles one, and explain why an interrupt vector is used.

  • An interrupt is a signal from hardware to the CPU, through an interrupt-request line, that an event requires CPU attention (e.g., I/O completion). It transfers control to an interrupt service routine (interrupt handler), which is part of the kernel.
  • Handling: the CPU senses the interrupt-request line after executing every instruction; on a signal it saves the state of the interrupted process (PC, registers), reads the interrupt number, uses it as an index into the interrupt vector and jumps to the handler in kernel mode; afterwards it restores the state and returns to the interrupted instruction.
  • Interrupt vector = a table (array) holding the addresses of the interrupt handlers, indexed by each interrupt's unique number → fast dispatch to the proper handler, with no generic routine needed to find the source first.
  • All modern operating systems are interrupt-driven (hundreds of interrupts per second).
X3-15Maskable vs nonmaskable interrupts; priority levelsCH3

Distinguish maskable and nonmaskable interrupts. What are interrupt priority levels for?

  • Most CPUs have two interrupt-request lines:
    • Nonmaskable — cannot be turned off; reserved for events such as unrecoverable memory errors and power failure.
    • Maskable — can be turned off by the CPU before executing critical instruction sequences that must not be interrupted; used by device controllers to request service, which can be delayed.
  • Interrupt priority levels let the CPU defer low-priority interrupts without masking all interrupts, and let a high-priority interrupt preempt the execution of a low-priority interrupt — interrupts are not all serviced the same way. A trap (software interrupt) gets a relatively low priority compared with device interrupts.
X3-16Programmed I/O vs DMA; DMA transfer stepsCH3

Why is DMA used instead of programmed I/O? Describe how a DMA transfer is set up and completed.

  • Programmed I/O: the CPU runs special I/O instructions to move one byte at a time between memory and a device — acceptable for slow devices (keyboard, mouse), but for fast devices and large transfers (disk) it wastes CPU time on data movement.
  • DMA: the DMA controller bypasses the CPU and transfers a whole block directly between the I/O device and memory; the CPU/OS only initializes it, which relieves the CPU to run other work concurrently.
  • Set-up: the OS writes a DMA command block into memory (source and destination addresses, read or write mode, number of bytes) and writes its location to the DMA controller; the controller uses bus mastering (grabs the bus, momentarily keeping the CPU out of main memory) and interrupts the CPU once, when the transfer is complete — not after every byte.
  • Six steps (disk → buffer X): (1) the driver is told to transfer disk data to buffer X; (2) the driver tells the disk controller to transfer C bytes to X; (3) the disk controller initiates the DMA transfer; (4) it sends each byte to the DMA controller; (5) the DMA controller writes the bytes to X, increasing the address and decreasing C until C = 0; (6) when C = 0, DMA interrupts the CPU to signal completion.
X3-17Dual-mode operation, mode bit, privileged instructionsCH3

What is dual-mode operation and why is it needed? How does the hardware support it, and what happens when a user program executes a privileged instruction?

  • Dual-mode operation separates user mode (user code) from kernel mode (OS code); it allows the OS to protect itself and other system components — the OS from errant users, and errant users from one another.
  • A mode bit provided by hardware shows the current mode: user = 1, kernel = 0. Some instructions are privileged — executable only in kernel mode (e.g., I/O control, timer management, interrupt management), and devices are accessed only in kernel mode, so user programs must request OS services through system calls.
  • A privileged instruction attempted in user mode is treated by the hardware as illegal and trapped to the OS; it is not executed.
  • Control starts in kernel mode; the mode is set to user mode before control passes to a user application and returns to kernel mode via an interrupt, a trap or a system call; return from a system call resets user mode.
X3-18Which operations must be privilegedCH3

Which of these must be privileged, and why? (a) set the value of the timer (b) read the clock (c) clear memory (d) issue a trap instruction (e) disable interrupts (f) modify entries in the device-status table (g) access an I/O device.

  • Privileged: (a), (c), (e), (f), (g) — set the timer, clear memory, disable interrupts, modify the device-status table, access I/O devices. A user program doing these could monopolize the CPU (timer, interrupts), wipe out the OS or other processes (clear memory), or bypass the OS's control of devices.
  • Not privileged: (b) read the clock (harmless, read-only) and (d) issue a trap instruction — a trap is exactly how a user program requests an OS service (system call), so it must work in user mode.
X3-19Timer: OS always regains controlCH3

How does the OS ensure that a user program cannot keep the CPU forever (e.g., one stuck in an infinite loop)?

  • With a timer: before giving control to a user program, the OS sets the timer to interrupt after a specified period (a counter decremented by the clock; an interrupt occurs when it reaches 0).
  • The timer interrupt transfers control back to the OS in kernel mode, which may treat it as a fatal error, give the program more time, or schedule another process (time slice expired).
  • Instructions that modify the timer are privileged, so a user program cannot turn it off — hence a user program always returns control to the OS.

X3-21System-call path: printf() to write()CH3

In terms of user mode and kernel mode, explain what happens when a program calls printf("hi\n").

  1. printf() is a C library (API) function running in user mode; it formats the text into a buffer and invokes the write() system call on fd 1 (buffering may delay this until a newline or flush).
  2. The write() wrapper puts the system-call number and parameters in registers and executes a trap → the hardware sets the mode bit to kernel mode (0) and jumps to the kernel's system-call handler.
  3. The kernel indexes the system-call table with the number, runs the write service routine (device driver) and stores the return value (bytes written, or −1).
  4. Return from the system call resets the mode bit to user mode (1) and execution continues after the call. If the device is busy, the process may block (running → waiting) while another process runs.
X3-22Beyond two modes: rings, VMM, machine switchCH3

How can dual-mode operation be extended beyond two modes? What is a machine switch?

  • Intel processors have four protection rings: ring 0 = kernel mode, ring 3 = user mode; rings 1 and 2 could run OS services but are rarely used. ARMv8 systems have seven modes.
  • CPUs that support virtualization have a separate mode for the virtual machine manager (VMM), with more privileges than user processes but fewer than the kernel.
  • A machine switch is the VMM's counterpart of a context switch: it saves the entire machine state of one guest OS — registers, PC and, unlike a context switch, any privileged hardware state — restores the new VM's machine state and jumps to its PC (inside its kernel or in a user application).
X3-23Process creation options; tree of processesCH3

When a parent creates a child, what are the options for (a) sharing resources, (b) execution, and (c) the child's address space? Give UNIX examples.

  • Processes form a tree of processes: a parent creates children, which create their own children; on Linux the root is systemd (PID 1), and each process has a unique pid. The child needs CPU time, memory, files and I/O devices, and the parent may pass it initialization data.
  • (a) Resource sharing: parent and children share almost all resources — fork() (the child gets copies of everything); children share a subset of the parent's resources — clone(); or they share no resources.
  • (b) Execution: the parent continues to execute concurrently with its children (shell runs a.out &), or the parent waits until some or all children have terminated (shell runs a.out and waits).
  • (c) Address space: the child is a duplicate of the parent (same program and data) — UNIX fork(); or the child has a new program loaded into it — exec() after fork().
X3-24fork() return values and why twoCH3

What does fork() return, and why must the parent and the child receive different values?

  • fork() takes no parameters; each process gets exactly one return value:
    • > 0 in the parent — the PID of the newly created child;
    • 0 in the child;
    • −1 in the original process if it fails — no child is created (errno is set).
  • The child duplicates the parent's entire address space, including the program counter, so both continue at the instruction right after fork() with identical code; the return value is the only way to tell which process is running, so the two can take different branches. The parent also learns the child's PID, needed later to wait for or terminate that child.
  • Which process runs first is decided by the CPU scheduler; their execution may interleave.
X3-25fork() steps, copy-on-write, clone()CH3

What steps does the kernel take to implement fork()? Why is this expensive, and how does Linux speed it up?

  • Steps: (1) create and initialize the PCB in the kernel (unique PID); (2) create a new address space (allocate memory); (3) initialize it with a copy of the entire contents of the parent's address space — time consuming; (4) inherit the parent's execution context (e.g., open files); (5) inform the CPU scheduler that the child is ready to run.
  • The copy is wasted when the child calls exec() immediately and discards it.
  • Copy-on-write (COW): parent and child share a single copy of the pages, and a page is copied only when either process writes to it. If exec() follows fork(), the pages never need to be copied → greatly speeds up process creation, while each process still behaves as if it had its own copy.
  • Linux implements fork() with the more general clone() system call, whose flags specify which resources parent and child share.
X3-26After fork(): copied, shared, differentCH3

After a successful fork(), what does the child get from the parent and what is different? Which of the stack, heap and shared-memory segments are shared?

  • Duplicated (the child gets its own copy): the address space — text, data, heap, stack, hence global and local variables; the program counter and registers; open file descriptors (referring to the same files and pipes); current and root directory, process resources, resource limits; customized signal handlers.
  • Different: the PID (and parent PID), the return value of fork(), running time and running state.
  • Stack and heap are copied, not shared — a change by one process is invisible to the other; of the three, only shared-memory segments are shared.
  • Because descriptors are inherited, a pipe created before fork() connects parent and child.

X3-30exec(): success, failure, execlp vs execvpCH3

What does a successful exec() do to the calling process? Does it create a new process or change the PID? When is the statement after exec() executed? Contrast execlp() and execvp().

  • exec() changes the program being run by the current process: it creates a new process image from an executable file, replacing the address space (text, data, heap, stack). It does not create a new process — the PID, PCB and open file descriptors stay the same (so redirection set up before exec() still applies).
  • A successful exec() never returns, so the code after it is never executed; only if it fails (e.g., program not found, no permission) does it return −1, and execution continues with the next statement.
  • execlp("ls", "ls", "-l", NULL) passes the arguments as a list (count known at compile time); execvp(args[0], args) passes an array (vector) (count known only at run time, as for PA1's parsed commands). p = search the PATH. argv[0] is the program name, and the list/array must end with NULL because exec has no argument count and stops at the NULL — hence PA1's array of 9 entries for at most 8 arguments.
X3-31Output: exec in a loop succeeds/failsCH3

How many processes are created and what is printed if (a) execlp() succeeds, (b) execlp() fails? What should the child do after a failed exec?

int main() {
    for (int i = 0; i < 3; i++) {
        pid_t pid = fork();
        if (pid == 0)
            execlp("echo", "echo", "hi", NULL);
    }
    while (wait(NULL) > 0)
        ;
    printf("done\n");
    return 0;
}
  • (a) exec succeeds: 4 processes (parent + 3 children). Each child becomes echo, prints hi and terminates — it never returns to the loop. The parent reaps all three and prints done once, last: hi, hi, hi, done.
  • (b) exec fails: execlp() returns −1 and the child continues the loop as a copy of the parent, so every process forks in each remaining iteration → 23=8 processes, done printed 8 times, no hi.
  • So a child must exit() after a failed exec (e.g., perror("exec"); exit(1);). In PA1 a missing exit leaves an extra shell process running (redundant processes), so the start and end PIDs no longer match.
X3-32Why a shell uses fork, exec, waitCH3

Why does a shell create a child with fork() and call exec() in the child, instead of calling exec() directly? Why is it useful that UNIX separates the two calls?

  • If the shell called exec() itself, its own image would be replaced by the command, and the shell would be gone when the command ended. So the shell fork()s a child, the child exec()s the command (overlays the new program), and the parent wait()s for the child, then reads the next command. For a background command (a.out &) the shell does not wait.
  • Most OSes create a process and load a program in one step; UNIX splits this into fork() and exec(). The child can therefore run code between the two calls to set up the new program's environment — I/O redirection with dup2(), connecting pipes, closing file descriptors — without affecting the shell. Copy-on-write keeps the extra fork() cheap.
X3-33PA1: cd and exit as built-insCH3

In PA1, why can cd not be executed with exec*(), and how is it implemented? Why is exit also a built-in?

  • The current working directory is a per-process attribute. If the shell forked a child to change directory, only the child's directory would change, and the change is lost when the child exits — a child cannot change its parent's directory, so the shell would stay where it was.
  • So cd is a built-in command run inside the shell process itself, without fork(), using chdir(path): 0 on success, −1 on error (print "Myshell cd command error"); it accepts absolute and relative paths, including . and ...
  • exit must terminate the shell process itself, so it is likewise handled inside the shell, not in a child.
X3-34PA1: why system() and popen() are bannedCH3

Why are system() and popen() forbidden in PA1? Why must pipes be used with open/read/write/close rather than fopen/fread/fwrite/fclose?

  • system() creates a system shell (e.g., bash) that runs the command, and the parent is blocked until it finishes; popen() also has a shell run the command concurrently and returns a FILE* for one-way communication with it. Using them hands all process creation, redirection and piping to another shell, defeating the purpose of PA1 (process management and IPC through system calls); they are detected by pattern matching and score 0 marks.
  • PA1 must use fork, exec*, wait, pipe, dup/dup2. FILE* is a high-level struct defined only in the C standard library and cannot be used in pipe operations; the low-level open/read/write/close work on file descriptors, which is what pipe() returns and dup2() manipulates.
X3-35PA1: Ctrl-C (SIGINT) handling with signal()CH3

How does PA1 customize Ctrl-C handling? What is a signal, and what does the handler receive?

  • A signal is a software-generated interrupt that notifies a process that an event has occurred. Ctrl-C makes the OS send SIGINT (signal number 2), whose default handler terminates the process; SIGINT is asynchronous (caused by an event outside the process).
  • PA1 overrides the default with a user-defined handler registered at start-up; the signal number is passed to the handler as its parameter:
void handler(int sig) {          /* sig = 2 */
    printf("Myshell (pid=%d) terminates"
           " by Ctrl-C with signal: %d\n",
           getpid(), sig);
    exit(0);
}
/* in main(): */
signal(SIGINT, handler);
  • Child processes inherit the customized handler through fork(). The PID printed must equal the start PID; otherwise redundant shell processes exist.
X3-36Termination: exit, wait, abort, cascadingCH3

Describe how a process terminates normally and how its parent obtains the exit status. Why might a parent terminate a child, and what is cascading termination?

  • After its last statement a process asks the OS to delete it with exit(), called directly or indirectly (the C run-time library calls exit() when main() returns). The OS de-allocates and reclaims its resources: memory (program, data, heap, stack), open files, I/O buffers.
  • It may return a status value (integer) to its waiting parent: pid = wait(&status); returns the PID of the terminated child (so the parent knows which child ended) and stores its exit status (exit(0) = normal, non-zero = error); wait() returns −1 if there are no children.
  • A parent may terminate a child (abort() on UNIX/Linux in the slides, TerminateProcess() on Windows; a process can also be killed with kill()) because the child has exceeded its allocated resources, the task assigned to the child is no longer required, or the parent is exiting and the OS does not allow a child to continue. The parent knows the child's PID from fork().
  • Cascading termination: some OSes do not allow a child to exist if its parent has terminated — when a process terminates, all its children must also be terminated, initiated by the OS. UNIX/Linux instead re-parent orphans to init/systemd.

X3-38Zombie or orphan? Two scenariosCH3

What happens to the child in each case? (A) The child calls exit(0) at once; the parent calls sleep(30) and then wait(NULL). (B) The child calls sleep(30) and then prints; the parent returns from main() at once without wait().

  • (A) The child is a zombie for about 30 seconds: it has terminated, but its PID, process-table entry and PCB (exit status) remain until the parent's wait(NULL) reaps it; then they are released.

X3-39Independent vs cooperating processesCH3

Distinguish independent and cooperating processes. Give reasons for allowing processes to cooperate.

  • Independent processes cannot affect or be affected by other processes; cooperating processes can affect or be affected by other processes (e.g., they share data), so they need an interprocess communication (IPC) mechanism to exchange data.
  • Reasons: information sharing — several applications need the same information (e.g., copy and paste); computation speedup — split a task into parallel subtasks (e.g., machine-learning jobs on multiple cores); modularity — divide system functions into separate processes or threads; convenience — a user can work on many tasks at once.

X3-41Bounded buffer: empty, full, BUFFER_SIZE − 1CH3

In the shared-memory bounded-buffer solution with in and out, when is the buffer empty or full, and why can it hold only BUFFER_SIZE - 1 items? With BUFFER_SIZE = 10, in = 3, out = 7, how many items are in the buffer?

  • Unbounded buffer: no practical limit on size (only the consumer may wait). Bounded buffer: fixed size — the consumer waits when it is empty, the producer waits when it is full.
  • Empty: in == out. Full: (in + 1) % BUFFER_SIZE == out. The producer stores buffer[in] and advances in = (in + 1) % BUFFER_SIZE; the consumer takes buffer[out] and advances out the same way; each busy-waits ("do nothing") while the buffer is full or empty, which wastes CPU cycles.
  • Since in == out already means empty, a completely full buffer would look identical, so one slot is always left unused → at most BUFFER_SIZE - 1 items.
  • Items = (in - out + BUFFER_SIZE) % BUFFER_SIZE = (3 − 7 + 10) % 10 = 6 (slots 7, 8, 9, 0, 1, 2).
  • Using all slots needs a shared count, but then count++ / count-- in two processes must be synchronized, or a race condition occurs (Chapter 6).
X3-42Message passing: link and design choicesCH3

  • Design choices for the link: direct or indirect communication (naming); synchronous (blocking) or asynchronous (non-blocking) send/receive; automatic or explicit buffering.
  • Fixed-size messages keep the system-level implementation straightforward but make programming harder; variable-size messages need a more complex system implementation but make programming simpler.

X3-47When to use ordinary vs named pipesCH3

Give a situation in which an ordinary pipe is more suitable than a named pipe, and one in which a named pipe is more suitable.

X3-48Why close unused pipe ends (EOF)CH3

Why must every process close the pipe ends it does not use? In the lab's ls | wc -l program, what happens if the process that runs wc does not close pfds[1]?

  • read() on a pipe returns 0 (end-of-file) only when every write end is closed in every process. If any process — even the reader itself — keeps a write end open, the reader blocks forever once the data is used up, and the program hangs.
  • In the lab the parent runs close(0); dup(pfds[0]); close(pfds[1]); wait(0); execlp("wc", ...). Without close(pfds[1]), wc holds a write end itself, so after ls exits, wc never sees EOF and never prints the count.
  • Rule from the slides: if the parent writes and the child reads, the parent must close the read end and the child must close the write end.
  • Note: since that parent calls wait(0) before wc reads, an ls output larger than the pipe capacity would make ls block on a full pipe, and both would wait forever.
X3-49What happens: blocking pipe and FIFO callsCH3

What happens when: (a) a process reads an empty pipe whose write end is still open; (b) it reads after all write ends are closed; (c) a process writes to a full pipe; (d) a process opens a FIFO for writing while no process has it open for reading; (e) two processes read the same FIFO?

  • (a) read() blocks until data is written — pipe read/write are blocking I/O.
  • (b) read() returns 0 = end-of-file (after any remaining data has been read).
  • (c) write() blocks until the reader removes data — a pipe has a limited size (lab: a 4 KB page; 64 KB on some systems).
  • (d) open() blocks until a reader opens the FIFO — FIFOs block until both ends are opened (O_NONBLOCK makes FIFO access non-blocking).
  • (e) Data read from a FIFO is discarded, so each byte goes to only one reader — a FIFO cannot broadcast a message. Writes of at most PIPE_BUF bytes are atomic; larger writes from several writers may interleave.

X3-51Two-way communication with ordinary pipesCH3

How can a parent and child communicate in both directions using ordinary pipes? Why not use one pipe?

  • An ordinary pipe is unidirectional, so create two pipes before fork(): p2c (parent → child) and c2p (child → parent).
  • Parent: close(p2c[0]); close(c2p[1]);, then writes to p2c[1] and reads from c2p[0]. Child: close(p2c[1]); close(c2p[0]);, then reads from p2c[0] and writes to c2p[1].
  • With one pipe, a process that writes and then reads may read back its own message. (A UNIX FIFO is likewise half-duplex; two FIFOs are used for simultaneous two-way traffic.)
  • Order the calls so that one side writes first; if both begin with a blocking read(), both wait forever.
X3-52Shell pipelines and multi-level pipesCH3

How does a shell implement ls | grep x? How is this extended to an n-segment pipeline such as PA1's ls | sort -r | sort | ...?

  • The shell calls pipe(fd) before forking, then forks two children: child 1 does dup2(fd[1], 1) (stdout → write end) and execs ls; child 2 does dup2(fd[0], 0) (stdin ← read end) and execs grep x (it prints only the lines of ls output containing x). Every process closes the pipe ends it does not use, and the shell closes both ends and waits for both children. Neither program knows about the pipe — pipes let separate tools be combined without being designed to work together.
  • n segments: in a for-loop, use n − 1 pipes and n children. Child i does dup2(pipe[i-1][0], 0) if i > 0 and dup2(pipe[i][1], 1) if i < n − 1, closes all pipe fds, and execvp()s its segment. The parent closes all pipe fds and waits for all n children (PA1: at most 8 segments).
X3-53dup vs dup2; I/O redirectionCH3

What do dup() and dup2() do? How is wc -l < in.txt > out.txt implemented, and why is the redirection done in the child after fork() and before exec()? What appears on the screen and in log.txt below?

X3-54Sockets, ports and the 4-tupleCH3

What is a socket? How does client–server communication work, and how are two connections from the same client host to the same web server told apart?

  • A socket is an endpoint for communication; two processes communicating over a network use a pair of sockets, one at each end. A socket is identified by an IP address (host) and a port number (process or application).
  • The server is always running with a well-known address and port, listening for requests; only clients can initiate communication. Ports below 1024 are well known, reserved for standard services (SSH 22, FTP 21, HTTP 80); a client picks an unused port number above 1024.
  • The 4-tuple (source IP address, source port, destination IP address, destination port) uniquely identifies a connection. Two connections from host 146.86.5.20 to web server 161.25.19.8 port 80 use different client ports (e.g., 1625 and 1626), so their 4-tuples differ.
X3-55Remote procedure calls (RPC)CH3

What is a remote procedure call (RPC), and what is it commonly used for? How does it differ from using sockets directly?

  • RPC abstracts the procedure-call mechanism for use between systems with network connections: a client calls a procedure on a remote host as if it were a local call. It is a message-based communication scheme to provide remote services.
  • A client-side stub packs the procedure name and parameters into a message and sends it to an RPC daemon on the server, which executes the procedure and sends the result back in a message.
  • Common use: distributed file systems, implemented as a set of RPC daemons and clients.
  • Sockets are low-level: they exchange an unstructured stream of bytes, and the application must impose structure; RPC hides the networking behind a procedure call.

X4-02shared vs private per-thread stateCH4

What do threads of the same process share, and what does each thread keep private? Why must each thread have its own stack and registers? [4.6, 4.16]

  • Shared by all threads of a process: code (text), data (global variables), heap, open files (file descriptors, network connections) and signals (signal handlers), i.e., the address space and OS resources.
  • Private to each thread (kept in its TCB): thread ID, program counter, register set and stack.
  • Why private: each thread is an independent flow of control at a different instruction, so it needs its own PC and registers; its stack holds its own call frames (parameters, temporary/local variables, saved PC), which would overwrite each other if shared.
  • Private does not mean protected: all stacks lie in the same address space, so a thread can still reach another thread's local variable through a pointer (e.g., main passes &counter to a thread).

State the four benefits of multithreaded programming and give an example of each. [4.7]

  • Responsiveness: may allow continued execution if part of a process (one thread) is blocked, which matters for interactive applications. E.g., a word processor keeps responding to keystrokes while another thread does background spelling and grammar checking.
  • Resource sharing: threads share the resources of a process by default (same address space), easier than shared memory or message passing between processes. E.g., a browser thread retrieves data from the network into a buffer that the display thread reads directly.
  • Economy: thread creation is much cheaper than process creation (less time and memory), and context switching between threads of a process is faster than between processes. E.g., a web server creates a thread, not a process, per client request.
  • Scalability: a process can take advantage of multicore architectures, because its threads run in parallel on different cores. E.g., data mining, graphics or AI work split across 8 cores.
X4-04thread creation and switching cheaperCH4

Explain why creating a thread, and switching between two threads of the same process, are cheaper than doing the same for processes. [4.4, 4.14]

Threads of a process share its address space and resources, so only the thread-specific state has to be created or switched.

  • Creation: a new process needs a new address space and copies of program, data and resources (PCB, memory, open files), so it is heavyweight. A new thread needs only a new TCB and a stack; the process-specific data structures are unchanged, so it is lightweight.
  • Context switch T1 → T2 (same process): save T1's register state and restore T2's; the address space remains the same, so the overhead is much smaller. Switching to a thread of a different process costs more, because the address space must also be switched.
X4-05disadvantages of threads vs processesCH4

Give two disadvantages of using multiple threads instead of multiple processes. When would separate processes be preferable? [4.9, 4.16]

(1) There is no protection between threads, and (2) shared data needs synchronization.

  • All threads run in one address space, and the address space is what encapsulates protection. A buggy thread can corrupt shared data or crash the whole process, e.g., an illegal memory access terminates the program and all its threads. Separate address spaces keep a buggy program from thrashing the entire system.
  • Shared globals and heap invite race conditions: if there is a data dependency, synchronization is required, and different paths of execution make testing and debugging difficult.
  • Prefer processes when tasks are independent or untrusted and fault isolation matters more than cheap sharing.
X4-06multicore programming challengesCH4

List and briefly explain the challenges of programming for multicore systems. [4.9]

Five challenges:

  1. Dividing tasks: find separate, concurrent tasks in the application.
  2. Balance: each task should perform an "equal" amount of work; a task that contributes little value may not be worth a separate core.
  3. Data splitting: data used by the tasks must be divided to run on separate cores.
  4. Data dependency: when one task uses data produced by another, synchronization is required.
  5. Testing and debugging: different paths of execution (many possible interleavings) make debugging difficult.
X4-07concurrency vs parallelismCH4

Distinguish concurrency from parallelism. Can there be concurrency without parallelism? Parallelism without concurrency? [4.9–4.10]

  • Concurrency supports more than one task making progress; on a single processor core, the scheduler provides concurrency by multiplexing over time.
  • Parallelism means a system can perform more than one task simultaneously, which requires multiple cores or processors.
  • Concurrency without parallelism: yes, e.g., 4 threads time-sliced on one core.
  • Parallelism without concurrency: no. Tasks running simultaneously are all making progress, so every parallel system is also concurrent (not vice versa).
  • E.g., 8 threads on 4 cores run in parallel across the cores and concurrently (interleaved) within each core.
X4-08data vs task parallelism, classify examplesCH4

Explain data and task parallelism using an array of N integers on a dual-core system. Classify: (a) a blur filter applied to four image quadrants on four cores; (b) a video player with one thread decoding video, one decoding audio and one handling the UI. [4.11]

  • Data parallelism distributes subsets of the same data across multiple cores and performs the same operation on each core. Thread A on core 0 sums elements 0 … N/2 − 1, thread B on core 1 sums N/2 … N − 1, and the two partial sums are added.
  • Task parallelism distributes threads (tasks) across cores, each thread performing a unique operation. On the same array, thread A computes the mean on core 0 while thread B finds the maximum on core 1.
  • They are not mutually exclusive: an application may use both (hybrid).
  • (a) Data parallelism (same filter, different subsets of the image). (b) Task parallelism (different operations).
X4-09Amdahl's law statement, limit 1/SCH4

State Amdahl's Law. What happens to the speedup as the number of cores N → ∞, and why does the serial portion have a "disproportionate effect"? [4.12–4.13]

speedup≤1/(S+(1−S)/N), where S = serial portion, 1 − S = parallel portion, N = number of processing cores. It gives the theoretical speedup in latency of a task at a fixed workload gained by adding cores.

  • As N → ∞, (1 − S)/N → 0, so the speedup approaches 1/S: the serial part takes the same time however many cores are added.
  • Disproportionate effect: with only 10% serial (S = 0.1), 8 cores give 1/(0.1+0.9/8)=1/0.2125≈4.71, not 8, and unlimited cores give at most 1/0.1=10.
X4-10Amdahl speedup, 60% parallelCH4

An application is 60% parallel. Using Amdahl's Law, find the maximum speedup on 4 cores, on 16 cores, and with unlimited cores. [4.12]

S = serial portion = 1 − 0.6 = 0.4 (the 60% is the parallel part).

  • N = 4: 1/(0.4+0.6/4)=1/(0.4+0.15)=1/0.55≈ 1.82
  • N = 16: 1/(0.4+0.6/16)=1/(0.4+0.0375)=1/0.4375≈ 2.29
  • N → ∞: 1/S=1/0.4= 2.5

Four times as many cores raise the speedup only from 1.82 to 2.29, because the 40% serial part dominates.

X4-13doubling cores vs halving serial partCH4

A program has serial fraction S = 0.2 and runs on N = 4 cores. Which helps more: doubling the cores or halving the serial portion? Does the answer change if N = 8? [4.12]

  • N = 4 (now 1/(0.2+0.8/4)=2.5): doubling the cores gives 1/(0.2+0.8/8)=1/0.3≈ 3.33; halving S gives 1/(0.1+0.9/4)=1/0.325≈ 3.08. So doubling the cores helps more.
  • N = 8 (now 1/0.3≈3.33): doubling the cores gives 1/(0.2+0.8/16)=1/0.25= 4; halving S gives 1/(0.1+0.9/8)=1/0.2125≈ 4.71. So halving the serial part helps more.
  • Rule: halving S beats doubling N exactly when S > 1/N (S·N > 1). As cores increase, the serial portion dominates, and only reducing S raises the ceiling 1/S (here from 5 to 10).
X4-14why real speedup is lowerCH4

Measured speedups on N cores are usually lower than Amdahl's Law predicts. Why? [4.9, 4.12]

Amdahl's Law is a theoretical upper bound (≤): it assumes the parallel part splits perfectly over N cores with zero overhead. In practice there is also:

  • Overhead of creating, managing and context-switching threads.
  • Synchronization: data dependencies force threads to wait for each other (locks, joins).
  • Imbalance: tasks rarely perform an "equal" amount of work, so the slowest thread decides the finish time.
  • Contention for shared memory, bus and caches, and other processes competing for the same cores.
X4-15multithreading on a single coreCH4

Can a multithreaded program finish faster than its single-threaded version on a single-core CPU? Explain. [4.9, 4.14]

Yes if the threads perform I/O (or otherwise block); no for purely CPU-bound work.

  • One core gives only concurrency (multiplexing over time), not parallelism, so CPU-bound threads gain no speedup and add context-switch overhead.
  • Threads enable overlap of I/O with other activities within a single program: one thread runs on the CPU while another thread of the process is doing I/O. The total time drops and the program stays responsive.
  • This needs kernel threads (one-to-one or many-to-many). Under many-to-one, a blocking I/O call blocks the entire process, so there is no overlap.
X4-16Thread Control Block contentsCH4

What does the OS keep in a Thread Control Block (TCB)? How is the TCB related to the PCB? [4.15]

Each thread has a TCB holding its private execution state, its scheduling and accounting information, and a pointer to its enclosing process (PCB).

  • Execution state: CPU registers, program counter, pointer to stack (saved here while the thread is not running).
  • Scheduling info: thread state, priority, CPU time. Accounting info.
  • Various pointers that link the TCB into scheduling queues.
  • Pointer to enclosing process (PCB): process-wide information (process ID, memory/address space, open files) stays in the PCB and is shared by all its threads, so the PID is not in the TCB.
X4-17process state with multiple threadsCH4

A process has three threads: one running, one waiting for a disk read, one ready. What is the state of the process? Where are the threads' TCBs? [4.17–4.18]

Each thread has its own state (new, ready, running, waiting, terminated), recorded in its TCB; the threads are scheduled individually, so one thread of the process can be running while another waits and a third is ready.

  • Running thread: executing on the CPU; it is resident in the registers.
  • Ready thread: its TCB is in the ready queue.
  • Waiting thread: its TCB is in the disk unit's device queue. TCBs are organized into queues based on their states, one queue per device/signal/condition, each with its own scheduling policy.

X4-19thread libraries, Pthreads specificationCH4

What is a thread library? Name the three primary thread libraries. Is Pthreads an implementation? [4.20]

A thread library provides the programmer with an API for creating and managing threads (user threads) in programs.

  • Three primary libraries: POSIX Pthreads (POSIX API, UNIX/Linux), Windows threads (Win32 API), Java threads (Java API).
  • Pthreads is a specification, not an implementation: the POSIX standard (IEEE 1003.1c) defines the API for thread creation and synchronization, and different UNIX-like OSes implement it differently.
  • User threads are the concurrent and modular entities of a program that the OS maps onto kernel threads.
X4-20pthread_create arguments, pthread_join purposeCH4

Explain the arguments of pthread_create() and the purpose of pthread_join(). What can go wrong if main() never calls pthread_join()? [4.20, 4.33]

pthread_create() starts a new thread that runs start_routine(arg); pthread_join() makes the caller wait until that thread terminates.

int pthread_create(pthread_t *tid,
                   const pthread_attr_t *attr,
                   void *(*start_routine)(void *),
                   void *arg);
  • tid receives the new thread identifier; attr holds the thread attributes (stack size, scheduling info; NULL or pthread_attr_init() = default); start_routine is the function where the thread begins execution; arg is the single void * argument passed to it. Returns 0 on success.
  • pthread_join(tid, &ret) blocks the caller until thread tid terminates and collects its return value (create/join strategy: the parent thread waits for its child thread).
  • Without a join, main may return first, and returning from main calls exit(), which terminates the whole process including all its threads. A worker may be killed before it finishes (e.g., sum is printed before it is computed).
  • Compile and link with gcc prog.c -lpthread.
X4-21passing arguments, returning thread resultsCH4

A start routine takes only one void * argument. How do you pass several values to a thread, and how does the thread return a result to the thread that joins it? [4.20, 4.33]

Pack the values in a struct, pass its address as arg, and return a pointer with return or pthread_exit(); the joining thread receives it through pthread_join().

struct args { int lo, hi; long sum; };
void *worker(void *p) {
    struct args *a = (struct args *)p;  /* cast back */
    a->sum = 0;
    for (int i = a->lo; i <= a->hi; i++) a->sum += i;
    return a;                     /* = pthread_exit(a) */
}
/* in main: */
struct args a = {1, 100, 0};  void *res;
pthread_create(&tid, NULL, worker, &a);
pthread_join(tid, &res);  /* res == &a; sum = 5050 */
  • Never return the address of the thread's local variable: it lives on the thread's private stack, which is gone once the thread terminates. Return heap memory (malloc), a global, or a field of the argument struct.
X4-22passing &i to threads bugCH4

void *show(void *arg) {

X4-23pthread_exit vs return vs exitCH4

In a multithreaded program, what is the difference between a thread calling pthread_exit(), returning from its start routine, and calling exit()? What happens when main() returns? [4.20, 4.33]

  • pthread_exit(v) or return v from the start routine terminates only the calling thread; v goes to the thread that calls pthread_join() on it. The other threads keep running.
  • exit() called by any thread terminates the entire process, i.e., all of its threads. Returning from main() is the same as calling exit().
  • So main() should pthread_join() its workers first, or end with pthread_exit(), which ends only the main thread; the process then ends when its last thread terminates.

X4-26blocking system call, many-to-one vs one-to-oneCH4

A process has 4 user threads on a 4-core machine. Thread T1 calls read() on a slow disk. What happens to T2–T4 under (a) the many-to-one model, (b) the one-to-one model? [4.22–4.23]

(a) Many-to-one: T2–T4 are blocked too, because the entire process is blocked. All four user threads are mapped to one kernel thread; T1's blocking system call blocks that kernel thread, and the OS has no other kernel thread of this process to schedule. Even before the call, only one thread can run at a time, so 3 cores are idle for this process (concurrency, no parallelism). (b) One-to-one: T2–T4 keep running. Each has its own kernel thread; only T1's kernel thread waits, and the others are scheduled in parallel on the other cores. This is why one-to-one provides the maximum concurrency.

X4-27why most OSes use one-to-oneCH4

The one-to-one model has more overhead than many-to-one, yet most operating systems (Windows, Linux) use it. Why? [4.23, 4.26]

It gives maximum concurrency and true parallelism, and its cost (a limit on the number of kernel threads) matters less as the number of cores grows.

  • A blocking thread does not block the others, and multiple threads run in parallel on multiprocessor or multicore systems.
  • Drawback: creating a user-level thread mandates creating a corresponding kernel thread; kernel threads consume resources (memory, I/O, etc.), so the number of threads per process may be restricted. But with an increasing number of processing cores, limiting the number of kernel threads has become less important.
  • It is simpler than many-to-many, which is most flexible but difficult to implement in practice.
X4-28many-to-many and two-level modelsCH4

Explain the many-to-many and two-level models. What do they offer over one-to-one, and why is many-to-many rarely used? [4.24–4.26]

  • Many-to-many multiplexes many user-level threads onto a smaller or equal number of kernel threads, specific to a particular application or machine: an application may be allocated more kernel threads on an 8-core system than on a 4-core system. The thread library decides which user thread runs on which kernel thread (process-contention scope, PCS).
  • It offers: programmers can create as many user threads as needed, not restricted by the number of kernel threads; the OS can create a sufficient number of kernel threads in advance (thread pool); a blocking call does not block the whole process; threads still run in parallel.
  • Two-level model: like many-to-many, but it also allows a user thread to be bound to a kernel thread, so that thread always has a kernel thread of its own.
  • Rarely used because it is most flexible but difficult to implement in practice, and with many cores one-to-one is good enough. Example: Windows with the ThreadFiber package.
X4-29LWP, scheduler activations, upcallsCH4

What is a lightweight process (LWP)? How do the kernel and the thread library cooperate under the many-to-many model?

  • An LWP is an intermediate data structure between user and kernel threads. To the user-thread library, an LWP appears to be a virtual processor on which the application can schedule a user thread to run (many-to-one / many-to-many mapping; this choice is PCS).
  • Each LWP is attached to a kernel thread, and it is the kernel threads that the OS schedules on the CPUs. If a kernel thread blocks (e.g., waiting for I/O), the LWP blocks as well, and so does the user thread running on it.
  • The OS coordinates with the thread library so that the number of kernel threads (LWPs) given to the process is dynamically adjusted for best performance. The textbook calls this scheduler activation: the kernel tells the library about events (e.g., a thread is about to block) by an upcall and gives it a new LWP, on which the library runs another user thread.
X4-30thread pool benefitsCH4

What is a thread pool? Why is serving requests from a thread pool better than creating a new thread for each request? [4.24]

A thread pool is a set of threads created in advance (at start-up) that wait in a pool for work. A request is handed to an idle pool thread, which returns to the pool when done instead of terminating. (The many-to-many model likewise lets the OS create a sufficient number of kernel threads in advance.)

  • Faster: an existing thread services the request at once, with no thread-creation delay per request.
  • Bounded resources: the pool limits the number of threads that exist at any one time, so a burst of requests cannot exhaust memory and CPU (each kernel thread consumes resources).
  • Flexibility: separating the task to be performed from the mechanics of creating the task allows different strategies for running it (e.g., run after a delay or periodically).
X4-31fork() and exec() in multithreaded processCH4

If one thread of a multithreaded process calls fork(), should the child duplicate all threads or only the calling thread? What happens when a thread calls exec()? [4.28]

It depends on whether the child calls exec(); some UNIX systems provide two versions of fork() for this reason.

  • If exec() is called immediately after forking, duplicate only the calling thread. Duplicating all threads is unnecessary, as the program specified in exec() will replace the entire process.
  • If the child does not call exec(), duplicate all threads, so the child is a full copy of the parent. (Linux/POSIX fork() duplicates only the calling thread.)
  • exec() works as normal: it replaces the entire process, including all threads (same PID). E.g., if a worker thread calls execlp("echo", "echo", "X", NULL) while main waits in pthread_join(), only X is printed and main never resumes.

X4-37what is a signal, handling stepsCH4

A signal is used in UNIX systems to notify a process that a particular event has occurred. A signal handler processes it in this pattern:

  1. The signal is generated by a particular event (e.g., division by 0, Ctrl-C, a timer expiring, process termination).
  2. The signal is delivered to a process (or thread).
  3. The signal is handled by one of two signal handlers: default or user-defined.
  • Every signal has a default handler that the kernel uses: some signals are ignored, while others (e.g., an illegal memory access) are handled by terminating the program.
  • Yes: a user-defined signal handler can override the default handler, e.g., signal(SIGINT, handler); (SIGKILL and SIGSTOP cannot be caught).
X4-38synchronous vs asynchronous signalsCH4

Distinguish synchronous and asynchronous signals, with two examples of each. Why is the first kind called synchronous? [4.29]

  • Synchronous signals are caused by an operation of the running process itself, e.g., an illegal memory access (segmentation fault) or a division by 0. They are delivered to the same process that performed the operation that caused the signal, which is why they are called synchronous.
  • Asynchronous signals are generated by an event external to the running process, e.g., terminating a process with Ctrl-C, a timer expiring, or another process calling kill().
  • A signal may be received either synchronously or asynchronously, depending on the source and the reason.
X4-39signal delivery in multithreaded processCH4

Where should a signal be delivered in a multithreaded process? A process has threads T1–T3; T2 divides by zero, and later the user presses Ctrl-C. Where should each signal go? [4.30–4.31]

The delivery method depends on the type of signal. There are four options:

  1. Deliver the signal to the thread to which the signal applies.
  2. Deliver the signal to every thread in the process.
  3. Deliver the signal to certain threads in the process.
  4. Assign a specific thread to receive all signals for the process.
  • T2's division by zero is synchronous, so it is delivered to the thread causing the signal (T2) and not to the other threads.
  • Ctrl-C terminates the process, so this asynchronous signal should be sent to all threads (T1–T3).
  • UNIX kill(pid, signal) delivers a signal to a process; Pthreads pthread_kill(tid, signal) delivers it to a specified thread. Hence "all signals go to all threads" is false.
X4-40asynchronous vs deferred cancellationCH4

What is thread cancellation? Compare asynchronous and deferred cancellation. Which is preferred, and why? [4.32]

Thread cancellation means terminating a thread before it has finished; the thread to be cancelled is the target thread.

  • Asynchronous cancellation terminates the target thread immediately, possibly in the middle of a critical update to shared data, which leaves the data inconsistent; the OS may not be able to reclaim all resources (memory, locks, files).
  • Deferred cancellation: the target thread periodically checks whether it should terminate, allowing it an opportunity to terminate itself in an orderly fashion. It is cancelled only at a safe cancellation point (e.g., blocking calls such as read() or close(), or pthread_testcancel()).
  • Deferred is preferred (and is the Pthreads default type) because the thread can finish its update and release its resources first.
X4-41pthread_cancel only requests cancellationCH4

Thread A calls pthread_cancel(tid) and then pthread_join(tid, NULL). Is the target terminated immediately? What if it is in a long computation loop with no function calls, or has cancellation disabled? [4.32–4.33]

No. Invoking pthread_cancel() only requests cancellation; the actual cancellation depends on the target thread's state and type.

  • The default type is deferred, so the request stays pending until the target reaches a cancellation point. A pure computation loop has none, so the thread is not cancelled until it calls, e.g., pthread_testcancel() or a blocking call that is a cancellation point.
  • If the thread has cancellation disabled, the cancellation remains pending until the thread enables it.
  • pthread_join() makes A wait until the target has actually terminated. Only a target whose type is set to asynchronous can be terminated immediately.
X4-42thread-local storageCH4

What is thread-local storage (TLS)? How does it differ from local variables and from global data? Give an example. [4.36]

Thread-local storage is data that is unique to each thread: every thread has its own copy.

  • vs global / static data: globals are shared by all threads of the process, while TLS gives each thread a private copy that, like static data, persists across function calls.
  • vs local variables: locals live on the stack and exist only during a single function invocation, while TLS is visible across all function invocations of that thread.
  • Example: each thread's own errno, or a unique transaction ID when each transaction is serviced by a separate thread. (Windows keeps TLS in the thread's TEB.)
X4-43Windows thread components, ETHREAD KTHREAD TEBCH4

List the components of a Windows thread and its primary data structures. Where does each data structure reside? [4.35–4.36]

Windows uses the one-to-one mapping: each user-level thread maps to an associated kernel thread. A thread has:

  • a thread ID, a register set (processor state), a program counter, separate user and kernel stacks, and a private data storage area used by run-time libraries and DLLs. The register set, stacks and private storage area are known as the context of the thread.
  • ETHREAD (executive thread block): pointer to the process the thread belongs to and to its KTHREAD; in kernel space.
  • KTHREAD (kernel thread block): scheduling and synchronization info, kernel-mode stack, pointer to the TEB; in kernel space.
  • TEB (thread environment block): thread ID, user-mode stack, thread-local storage; in user space.
X4-44Linux tasks, task_struct vs WindowsCH4

How does Linux represent threads? Contrast Linux with Windows for a process that has two threads. [4.37]

Linux does not differentiate between threads and processes: each is a task. A thread is a process that may share certain resources (e.g., the address space) with other tasks; each thread has its own unique task_struct and appears as a normal process.

  • Windows (explicit kernel support for threads): one PCB describes the shared resources (address space, open files) and points to the two threads' TCBs, each describing the resources that thread alone possesses.
  • Linux: simply two tasks with normal task_struct structures, set up to share resources.
X4-45clone() flags vs fork()CH4

How does Linux create a thread with clone()? Explain the flags and how clone() differs from fork(). [4.38]

Threads are created like normal tasks, except that clone() is passed flags naming the resources the child task shares with its parent: clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND, 0);

  • CLONE_VM: share the address space; CLONE_FS: share file-system information (e.g., current directory); CLONE_FILES: share the open files (file descriptors); CLONE_SIGHAND: share the signal handlers. With these flags, the child task behaves like a thread.
  • Instead of copying all data structures like fork(), the new task points to the data structures of the parent task, depending on the set of flags.
  • With no sharing flags, it behaves like a separate process: a normal fork() can be implemented as clone(SIGCHLD, 0) (SIGCHLD is the signal sent to the parent when the child terminates).

X5 · Ch5 CPU Scheduling

X5-01CPU–I/O burst cycle and burst distributionCH5

Describe the CPU–I/O burst cycle. What does the histogram of CPU-burst times show, and why does it matter for scheduling?

  • Process execution consists of a cycle of CPU execution and I/O wait — a CPU burst followed by an I/O burst, alternating until the process ends. While one process waits for I/O, the CPU scheduler gives the CPU to another ready process, so some process is running at all times → maximize CPU utilization (the goal of multiprogramming).
  • Measured CPU bursts follow a long-tail distribution: many short CPU bursts and a small number of long ones. An I/O-bound program has many short CPU bursts; a CPU-bound program has a few long CPU bursts.
  • This distribution is important for designing the scheduling algorithm, e.g., choosing the RR quantum (about 80% of bursts shorter than q) and favouring short bursts (SJF, MLFQ) to cut the average waiting time.
X5-02Distinguish I/O-bound from CPU-bound processesCH5

Why is it important for the scheduler to distinguish I/O-bound processes from CPU-bound processes?

Because they use the CPU very differently: an I/O-bound process runs only short CPU bursts and seldom uses its full quantum, while a CPU-bound process runs long bursts and uses its whole quantum.

  • Giving I/O-bound processes higher priority lets them start their next I/O quickly, keeping I/O devices busy and giving short response time to interactive jobs; the CPU-bound process uses the CPU while they wait → better CPU and device utilization.
  • Treating them alike (e.g., FCFS) makes I/O-bound jobs wait behind a CPU-bound one (convoy effect) and leaves the devices idle.
  • MLFQ makes this distinction automatically: CPU-bound jobs sink to lower queues, I/O-bound jobs stay near the top.
X5-03Four scheduling decision points, which preemptiveCH5

List the four situations in which CPU-scheduling decisions take place. Which of them are preemptive?

CPU scheduling may take place when a process:

  1. switches from running to waiting (e.g., I/O request, wait());
  2. terminates;
  3. switches from running to ready (e.g., an interrupt — timer / quantum expiry);
  4. switches from waiting to ready (e.g., I/O completion), or a new process arrives in the ready queue (new → ready) with a higher priority.

Cases 1 and 2 are non-preemptive — the process gives up the CPU voluntarily and a new process must be selected. Cases 3 and 4 are preemptive — the CPU can be taken away involuntarily. A scheduler that acts only in cases 1 and 2 is non-preemptive (cooperative).

X5-04Preemptive vs non-preemptive scheduling issuesCH5

Distinguish preemptive and non-preemptive scheduling. What problems does preemption introduce?

  • Non-preemptive: once a process gets the CPU it keeps it until it terminates or blocks (releases it voluntarily). Simple, low overhead, but a long process can monopolize the CPU (poor response time, convoy effect). E.g., FCFS, SJF.
  • Preemptive: the OS can take the CPU away on a timer interrupt (quantum expiry) or when a higher-priority / shorter process becomes ready. Better response time, no monopolization. E.g., RR, SRTF, preemptive priority, MLFQ.
  • Problems of preemption: (1) more context switches (overhead); (2) access to shared data — a process preempted while updating shared data can leave it inconsistent (race condition), so synchronization is needed; (3) preemption while in kernel mode — kernel data structures may be left inconsistent; (4) interrupts during crucial OS activities — such code must be protected (e.g., interrupts disabled).
X5-05Dispatcher and dispatch latencyCH5

What is the dispatcher and what does it do? What is dispatch latency, and why should it be small?

  • The dispatcher is the module that gives control of the CPU to the process selected by the CPU scheduler. It involves: (1) switching context from one process to another; (2) switching to user mode; (3) jumping to the proper location in the user program to restart it.
  • Dispatch latency is the time it takes for the dispatcher to stop one process and start another running. It is pure overhead paid on every context switch (typically hundreds per second, visible with vmstat on Linux), so the dispatcher must be as fast as possible.
  • The scheduler decides which process runs (policy); the dispatcher performs the switch (mechanism).
X5-06Scheduling criteria to maximize or minimizeCH5

Define the CPU-scheduling criteria and state whether each should be maximized or minimized.

Criterion Definition Goal
CPU utilization fraction of time the CPU is busy maximize
Throughput number of processes completed per unit time maximize
Turnaround time time to execute a process = completion − arrival (waiting + CPU + I/O time) minimize
Waiting time total time spent waiting in the ready queue = turnaround − CPU burst minimize
Response time time from submission until the first response is produced (this course: end of first run − arrival) minimize

The scheduling algorithm does not change CPU-burst or I/O time; it only changes the waiting time in the ready queue. Usually the average is optimized, and criteria can conflict (e.g., throughput favours short processes).

X5-07Response time definition and computationCH5

Define response time. How is it computed in this course for RR and for non-preemptive algorithms, and why is it important?

  • Response time is the amount of time from when a request is submitted until the first response is produced; in this course RT = completion of the first run on the CPU − arrival time.
  • RR / MLFQ: the first run ends at the end of the first quantum (or at completion if the burst < q). E.g., RR q = 4 with P1 24, P2 3, P3 3 (all at 0): RT = 4, 7, 10 → avg 7 (FCFS: 24, 27, 30 → avg 27).
  • Non-preemptive (FCFS, SJF, non-preemptive priority): the first run is the whole burst, so RT = turnaround time.
  • It matters for interactive (time-sharing) systems, where users need quick feedback; RR and MLFQ give short response times, while turnaround time matters more for batch jobs.
X5-08Conflicting scheduling criteriaCH5

Explain how these pairs of criteria conflict: CPU utilization vs response time; average turnaround vs maximum waiting time; I/O device utilization vs CPU utilization.

Scheduling criteria conflict, so an algorithm improves some at the expense of others:

  • CPU utilization vs response time: utilization is highest when context switches are rare (long quanta, little overhead), but short response time needs frequent switching (short quanta), which adds overhead.
  • Average turnaround vs maximum waiting time: average turnaround is minimized by running the shortest jobs first (SJF), but long jobs may then wait indefinitely (starvation), so the maximum waiting time grows.
  • I/O device utilization vs CPU utilization: CPU utilization is maximized by letting CPU-bound jobs run long without switching; I/O utilization is maximized by dispatching I/O-bound jobs as soon as they are ready to start their next I/O, which means more context switches.
  • In general, performance and fairness are often at odds: optimizing turnaround (SJF) sacrifices fairness; RR is fair but has a longer average turnaround.
X5-09FCFS and the convoy effectCH5

Describe FCFS scheduling. What is the convoy effect, and why is FCFS unsuitable for interactive systems?

  • FCFS serves processes in their order of arrival to the ready queue (FIFO). It is non-preemptive: a process keeps the CPU until it completes its current CPU burst. It is simple and starvation-free.
  • Convoy effect: short processes get stuck behind a long process, so the average waiting time is long and depends purely on the arrival order — bursts 24, 3, 3: order P1, P2, P3 → avg WT (0 + 24 + 27)/3 = 17; order P2, P3, P1 → (6 + 0 + 3)/3 = 3. With one CPU-bound and many I/O-bound processes, the I/O-bound ones wait behind the CPU-bound one → low I/O device utilization (and later an idle CPU).
  • Unsuitable for interactive systems: without preemption, a process cannot be guaranteed a share of the CPU at regular intervals, so response time is poor.
X5-10Round-robin mechanism and waiting boundCH5

Explain how Round-Robin scheduling works. What does it guarantee with n processes and time quantum q?

  • RR is FCFS with preemption: each process gets a small unit of CPU time, the time quantum q (usually 10–100 ms). When the quantum expires, a timer interrupt preempts the process and it is added to the tail of the ready queue; if its (remaining) burst is shorter than q, it releases the CPU itself and the next process runs at once.
  • With n ready processes, each gets 1/n of the CPU time in chunks of at most q, and no process waits more than (n − 1)q time units for its next turn (context-switch time ignored).
  • RR is fair (FIFO order, equal shares), gives good response time for interactive jobs and has no starvation; its average waiting time can be long.
  • Conventions: a new arrival at the same instant as a quantum expiry enters the ready queue first; if the queue is empty when the quantum expires, the process simply continues.
X5-11Choosing q from the waiting boundCH5

Ten interactive processes share a CPU under RR, and each must wait at most 90 ms in the ready queue before running again. Find the largest quantum (a) ignoring context switches, (b) if every context switch costs 1 ms.

(a) RR bound: no process waits more than (n − 1)q → (10−1)q≤90 → q ≤ 10 ms. (b) Between two turns of a process, the other n − 1 processes each run one quantum and n context switches occur → worst wait = (n−1)q+ns: 9q+10×1≤90 → q≤80/9 → q ≤ 8.9 ms.

  • Trade-off: a smaller q gives a tighter bound (better response) but more switching overhead (efficiency q/(q + s)).
X5-12Time quantum size effects, 80% ruleCH5

How does the size of the time quantum affect RR performance? State the rule of thumb for choosing it.

  • q too large (larger than every CPU burst) → each burst finishes in its first quantum → RR degenerates to FCFS.
  • q too small → too many context switches; q must be large with respect to the context-switch time (usually < 10 µs), otherwise the overhead is too high. In the limit (tiny q, zero switch cost) RR becomes processor sharing: each of n processes appears to have its own processor running at 1/n the speed.
  • Average turnaround time does not necessarily improve as q increases; it improves when most processes finish their CPU burst within a single quantum. E.g., bursts 6, 3, 1, 7 (all at 0): avg TAT = 11.0 (q = 1), 10.75 (q = 3), 12.25 (q = 5), 10.5 (q ≥ 6).
  • Rule of thumb: about 80% of CPU bursts should be shorter than the time quantum q.
X5-13RR CPU efficiency with context-switch overheadCH5

  • q = 10 ms: 10/10.1 = 99.0%; q = 1 ms: 1/1.1 = 90.9%; q = 0.1 ms: 0.1/0.2 = 50% → a quantum close to the switch time wastes the CPU. (A process that blocks after a burst b < q gives b/(b + s).)

(b) Each 10 ms I/O finishes before the task's next turn, so the CPU always has a ready task.

  • q = 1 ms: every task, I/O-bound or CPU-bound, runs 1 ms and then a 0.1 ms switch follows → U = 1/1.1 = 90.9%.
  • q = 10 ms: one round = 10 × (1 + 0.1) for the I/O-bound tasks + (10 + 0.1) for the CPU-bound task = 21.1 ms, containing 20 ms of useful work → U = 20/21.1 = 94.8%.
  • A larger quantum means fewer switches per unit of work → higher utilization, at the cost of response time.

X5-16SJF optimality and proof sketchCH5

Describe SJF scheduling and explain why it is optimal.

  • SJF (shortest-next-CPU-burst) associates each process with the length of its next CPU burst and runs the process with the shortest next burst (ties → FCFS). The idea: get short jobs out of the system sooner — a big gain for short jobs, a small cost for long ones.
  • SJF is optimal: it gives the minimum average waiting time for a given set of processes.
  • Proof sketch: moving a short process before a long one decreases the waiting time of the short process more than it increases the waiting time of the long process. Swapping an adjacent pair (long L before short S) changes the total waiting time by S − L < 0, so repeated swaps towards shortest-first can only reduce the average.
  • E.g., bursts 6, 8, 7, 3 (all at 0): SJF 0 P4 3 P1 9 P3 16 P2 24 → avg WT (3 + 16 + 9 + 0)/4 = 7, versus (0 + 6 + 14 + 21)/4 = 10.25 in FCFS order.
X5-17SJF implementation difficulty and approximationCH5

Why is SJF difficult to implement in practice? How can it be approximated, and what other drawbacks does it have?

  • The difficulty is knowing the length of the next CPU request — the scheduler cannot see the future, so SJF/SRTF are hard to implement and are mainly used as a benchmark for practical algorithms.
  • Approximation: predict the next CPU burst from the lengths of previous bursts using exponential averaging, τn+1​=αtn​+(1−α)τn​, then pick the process with the shortest predicted next burst (a wrong prediction gives a sub-optimal schedule).
  • SJF can be applied to an entire program (e.g., a run-time estimate supplied with a batch job) or to the current CPU burst.
  • Other drawbacks: starvation of long processes if shorter ones keep arriving; fairness cannot be enforced.
X5-18Exponential averaging formula and alphaCH5

X5-21SRTF definition and comparison with SJFCH5

Describe SRTF scheduling. When must the scheduler be invoked, and how does SRTF compare with SJF?

  • SRTF (shortest-remaining-time-first) is preemptive SJF: when a process joins the ready queue (new → ready, or waiting → ready after I/O) with a CPU burst shorter than the remaining time of the running process, it preempts the running process (equal remaining time → no preemption).
  • Hence the scheduler must run at every arrival to the ready queue (scheduling condition 4), not only at completions.
  • SRTF is optimal among preemptive algorithms for average waiting time and is always at least as good as SJF; if all processes arrive at the same time, SRTF = SJF; with equal bursts both behave like FCFS.
  • Drawbacks: needs the (predicted) burst length, causes more context switches, and can starve long processes if short ones keep arriving.

X5-23Priority scheduling and its relation to SJFCH5

Describe priority scheduling (preemptive and non-preemptive). How is SJF related to it?

  • Each process has a priority number; the CPU is allocated to the process with the highest priority (smallest integer = highest priority unless stated otherwise); equal-priority processes are scheduled in FCFS order (or RR).
  • Preemptive: a newly arrived process with a higher priority preempts the running process. Non-preemptive: a higher-priority arrival is put at the head of the ready queue and waits until the running process finishes its burst.
  • SJF is a special case of priority scheduling where the priority is the inverse of the predicted next CPU burst (shorter burst = higher priority); SRTF is its preemptive form.
  • Main problem: starvation (indefinite blocking) of low-priority processes; solution: aging.
X5-24Starvation and agingCH5

What is starvation? Explain how aging prevents it, with a numerical example.

  • Starvation (indefinite blocking): a process is ready to run but waits indefinitely for the CPU, because there are always higher-priority processes (or, in SJF/SRTF, shorter jobs) ahead of it.
  • Aging: gradually increase the priority of a process the longer it waits, so it eventually becomes high enough to run (implemented with a timer for each process in the ready queue).
  • Example: priorities range from 127 (lowest) to 0 (highest); raise a waiting process's priority by 1 every second → even a priority-127 process reaches priority 0 within 127 s (about 2 minutes), so its waiting time is bounded.
  • In MLFQ, aging is done by moving long-waiting jobs to a higher queue (e.g., periodically moving all jobs to the top queue).

X5-27Dynamic priority alpha beta gives FCFS or LIFOCH5

A preemptive scheduler uses dynamic priorities (larger number = higher): a waiting process's priority changes at rate α, a running process's at rate β, and every process enters the ready queue with priority 0. Which algorithm results from (a) β > α > 0, (b) α < β < 0?

(a) β > α > 0 → FCFS. Every priority rises from 0, so a new process (priority 0) is lower than every process already in the system and never preempts; the running process rises fastest (β > α), so it is never preempted; among the waiting processes, the one that has waited longest has the highest priority → processes run in arrival order. (b) α < β < 0 → LIFO (last-in, first-out). Every priority falls from 0, so a new process (priority 0) is higher than all existing ones and preempts the running process immediately → the most recently arrived process always runs first.

X5-28Least-recent-CPU policy favours I/O-boundCH5

A scheduler favours the processes that have used the least processor time in the recent past. Why does it favour I/O-bound processes, yet not permanently starve CPU-bound processes?

  • It favours I/O-bound processes because they run only short CPU bursts before blocking for I/O, so their recent CPU usage is small and they get high priority.
  • CPU-bound processes do not starve permanently because the I/O-bound processes give up the CPU frequently to do their I/O, and the CPU-bound process runs in those gaps. Also, usage is measured only over the recent past: while a CPU-bound process waits, its recent usage falls and its priority rises (an aging effect).
X5-29Multilevel queue schedulingCH5

Describe multilevel queue scheduling. How is the CPU shared among the queues?

  • The ready queue is partitioned into separate queues based on process type (e.g., real-time, system, interactive, batch). The priority is assigned statically: a process remains in the same queue for its whole runtime.
  • Each queue can have its own scheduling algorithm (e.g., RR for interactive/foreground, FCFS for batch/background).
  • Scheduling among the queues: (1) fixed-priority preemptive scheduling — a lower queue runs only when all higher queues are empty, and an arrival in a higher queue preempts it → low queues can starve; or (2) time slicing — each queue gets a certain share of CPU time (e.g., 60%, 20%, 10%, 10%).
  • Priority scheduling with RR is easily implemented as a multilevel queue (one RR queue per priority level). Low scheduling overhead, but inflexible.

X5-31MLFQ defining parametersCH5

What parameters define a multilevel feedback queue scheduler?

An MLFQ scheduler is defined by:

  1. the number of queues;
  2. the scheduling algorithm for each queue (e.g., RR with its own quantum per queue, FCFS in the last queue);
  3. the method used to determine when to upgrade a process to a higher-priority queue (e.g., aging);
  4. the method used to determine when to demote a process to a lower-priority queue (e.g., after it uses a full quantum);
  5. the method used to determine which queue a process will enter when it needs service (e.g., every new job enters Q0).

Because a process can move between queues, aging can be implemented this way, which gives MLFQ its flexibility.

X5-32MLFQ rules: demotion, preemption, head of queueCH5

MLFQ with Q0 (RR, q = 8 ms), Q1 (RR, q = 16 ms), Q2 (FCFS). (a) Where does a new job go, and when is it demoted? (b) A Q1 job that has used 5 ms of its quantum is preempted by a new arrival: where does it go, with how much quantum? (c) Can a Q1 job preempt a Q2 job? (d) Which jobs never reach Q2?

(a) A new job enters the tail of Q0 (RR, FCFS order) and preempts a running Q1 or Q2 job. A job that uses its full quantum without finishing is demoted to the tail of the next queue (Q0 → Q1 → Q2). A running Q0 job is never preempted by an arrival (the arrival waits in Q0). (b) It returns to the head of Q1 and later resumes with its remaining quantum, 16 − 5 = 11 ms; it is not demoted and does not get a fresh quantum (a job never receives more than 16 ms in Q1). A preempted Q2 job returns to the head of Q2 with its remaining burst. (c) No. No job arrives directly at Q1; a job enters Q1 only by using a full Q0 quantum, i.e., while a Q0 job is running. A Q2 job runs only when Q0 and Q1 are empty, and only a new arrival to Q0 can preempt it. (d) Jobs with a CPU burst ≤ 8 + 16 = 24 ms finish within Q0 and Q1. This is how MLFQ approximates SRTF: CPU-bound jobs drop like a rock; short-running I/O-bound jobs stay near the top.

X5-33MLFQ disadvantages and remediesCH5

What are the disadvantages of MLFQ, and how can they be handled?

  • Starvation: with fixed priority among queues, long CPU-bound jobs in the lowest queue may never run if new or short jobs keep arriving → handled by aging / reshuffling jobs among the queues periodically, e.g., after some period, move all jobs to the top queue.
  • Complexity: it is the most general but most complex scheduler — the number of queues, each queue's quantum and algorithm, and the upgrade/demote/entry rules must all be chosen and tuned for the workload.
  • Changing behaviour: a job demoted during a CPU-bound phase stays at low priority even if it later becomes interactive, unless an upgrade (aging) rule moves it back up.
  • (Its advantages: no prior knowledge of burst times, good response time for interactive jobs, SJF/SRTF-like performance, and fair progress for CPU-bound jobs.)

X5-37Equivalences between scheduling algorithmsCH5

State the relation between: (a) RR and FCFS; (b) SJF and priority; (c) priority and FCFS; (d) MLFQ and FCFS; (e) SJF/SRTF and FCFS; (f) RR and SJF.

  • (b) SJF = priority scheduling with priority = inverse of the predicted next CPU burst; SRTF = preemptive priority on the remaining time.

X5-38How FCFS, RR, MLFQ treat short jobsCH5

Explain how much FCFS, RR and MLFQ discriminate in favour of short processes.

  • FCFS — discriminates against short jobs: a short job that arrives after long jobs must wait for all of them (convoy effect).
  • RR — treats all jobs equally: each job gets the same quantum in turn, so a short job finishes after only a few quanta and leaves the system sooner, but it gets no extra priority.
  • MLFQ — strongly favours short jobs: short (interactive, I/O-bound) jobs finish in the high-priority top queues, while long CPU-bound jobs are demoted to lower queues — similar to SJF/SRTF without knowing the burst lengths.

X5-42Memory stall and chip multithreadingCH5

What is a memory stall, and how do multithreaded multicore processors (CMT) exploit it? How many logical CPUs does the OS see on a quad-core processor with 2 hardware threads per core?

  • Multicore = multiple processor cores on the same chip: faster and consumes less power, but complicates scheduling.
  • Memory stall: when a processor accesses memory it spends a significant amount of time waiting for the data, because modern processors are much faster than memory, especially on a cache miss.
  • Chip multithreading (CMT; Intel: hyperthreading) gives each core multiple hardware threads, each with its own architectural state (PC, register set), so each appears to the OS as a logical CPU. If one hardware thread stalls on memory, the core switches to another hardware thread, so useful work continues during the stall.
  • Logical CPUs = cores × hardware threads per core: 4 × 2 = 8 (dual-core dual-threaded = 4; UltraSPARC T3: 16 × 8 = 128).
X5-43Two levels of multicore thread schedulingCH5

Describe the two levels of scheduling on a multithreaded multicore processor, and the full mapping from user threads to cores.

  1. OS level: the operating system decides which software (kernel) thread runs on each logical CPU (hardware thread) — this is the CPU scheduling of this chapter, using any algorithm.
  2. Core level: each core decides which of its hardware threads runs on the physical core, e.g., simple round-robin (UltraSPARC T3).
  • Full mapping: user thread → LWP / kernel thread (thread library, PCS) → kernel (software) thread → hardware thread / logical CPU (OS, SCS) → hardware thread → physical core (core hardware, typically RR).
X5-44Processor affinity: soft, hard, NUMACH5

What is processor affinity? Distinguish soft and hard affinity, and explain how NUMA affects it.

  • Processor affinity: a thread has affinity for the processor it runs on, because that processor's cache holds the thread's recently accessed memory. Migration means invalidating and repopulating caches (high cost), so most SMP systems try to avoid migrating processes; per-processor ready queues provide affinity for free.
  • Soft affinity: the OS attempts to keep a process on the same processor but does not guarantee it — the process may migrate during load balancing.
  • Hard affinity: a process specifies the subset of processors on which it may run (e.g., Linux sched_setaffinity()); many systems, such as Linux, provide both.
  • NUMA: a CPU accesses its local memory faster than remote memory, so a thread should run on a CPU near its memory → affinity to both the processor and the memory.
X5-45Load balancing: push, pull, affinity conflictCH5

Explain push and pull migration. Why does load balancing conflict with processor affinity?

  • Load balancing keeps the workload evenly distributed across processors; it is needed when each processor has its own private ready queue (a common queue balances itself).
  • Push migration: a specific task periodically checks the load on each processor and, if it finds an imbalance, pushes tasks from overloaded CPUs to idle or less-busy CPUs.
  • Pull migration: an idle processor pulls a waiting task from a busy processor.
  • They are not mutually exclusive — often both are implemented (e.g., Linux CFS).
  • Conflict: a migrated thread loses its cache contents (and on NUMA its local memory), so load balancing often counteracts the benefits of processor affinity — a natural tension between balancing the load and minimizing memory access time (e.g., migrate only when the imbalance exceeds a threshold).
X5-46Hard versus soft real-timeCH5

Distinguish hard and soft real-time systems. What must a real-time CPU scheduler support?

  • Hard real-time: stricter — a task must be serviced by its deadline; service after the deadline has expired is the same as no service at all (e.g., airbag or flight control).
  • Soft real-time: no guarantee as to when a critical real-time process will be scheduled; it guarantees only that the real-time process will be given preference over non-critical processes (e.g., video streaming).
  • Real-time scheduling demands performance guarantees — predictability. The scheduler must support a priority-based algorithm with preemption, so a ready high-priority real-time task gets the CPU at once; but a preemptive priority-based scheduler alone guarantees only soft real-time. Hard real-time also needs deadline guarantees (admission control, RM/EDF analysis).

  • Event latency: the time from when an event occurs to when it is serviced. Two latencies affect real-time performance:
  • Interrupt latency: the time from the arrival of an interrupt at the CPU to the start of the routine that services it — the CPU finishes the current instruction, determines the interrupt type and saves the state of the current process. X5-48Periodic tasks, utilization, admission controlCH5

Describe the characteristics of a periodic real-time task. What is the CPU utilization of a task set, and what is admission control?

  • A periodic task requires the CPU at constant intervals (periods): processing time t, deadline d, period p, with 0 ≤ t ≤ d ≤ p; its rate is 1/p. One job is released every p time units and must finish by its deadline (often d = p, i.e., by the start of the next period).
  • CPU utilization of task i = ti​/pi​; total U=∑i​ti​/pi​. E.g., (t, p) = (20, 50) and (35, 100): U = 0.40 + 0.35 = 75%. If U > 1, the CPU is overloaded and some deadlines must be missed.

X5-49Rate-monotonic scheduling and missed deadlinesCH5

Explain rate-monotonic (RM) scheduling. Why can RM miss a deadline even when U < 1?

  • RM schedules periodic tasks using a static priority policy with preemption: priority = inverse of the period — shorter period (higher rate) = higher priority, because tasks that need the CPU more often get higher priority. Priorities never change.
  • RM is optimal among static-priority algorithms: if a task set cannot be scheduled by RM, no other static-priority algorithm can schedule it. It handles only periodic tasks with a constant processing time.
  • Deadlines can be missed with U < 1, because the static priority ignores how close each deadline is. E.g., P1 (t = 25, p = 50), P2 (t = 35, p = 80): U = 0.50 + 0.44 = 94%; P1 preempts P2 at 50: 0 P1 25 P2 50 P1 75 P2 85 → P2 misses its deadline 80, finishing at 85.
  • RM is guaranteed only if U≤N(21/N−1) (0.828 for N = 2; tends to ln 2 ≈ 0.693 for large N) — a sufficient, not necessary, condition.
X5-50Earliest-deadline-first schedulingCH5

Explain EDF scheduling and its advantages over RM. Why can it not reach 100% CPU utilization in practice?

  • EDF assigns priorities dynamically according to the deadline: the earlier the (absolute) deadline, the higher the priority; priorities are re-evaluated whenever a job becomes runnable; it is preemptive.
  • EDF does not require processes to be periodic, nor a constant amount of CPU time per burst — the only requirement is that a process announces its deadline when it becomes runnable.
  • Theoretically optimal: it can schedule processes so that each meets its deadline with CPU utilization up to 100% (U ≤ 1 when deadline = period). E.g., P1 (25, 50), P2 (35, 80): 0 P1 25 P2 60 P1 85 P2 100 P1 125 P2 145 idle 150 — at t = 50, P2's deadline 80 is earlier than P1's 100, so P2 continues → no deadline missed (RM misses 80).
  • In practice 100% is impossible because of the cost of context switching and interrupt handling.

  • EDF wins because its dynamic priorities follow the deadlines, whereas RM's static priority ran P1 (deadline 10) ahead of P2 (deadline 7).

X6-01Race condition: counter++ / counter-- interleavingCH6

Define a race condition. Using counter++ (producer) and counter-- (consumer) with counter = 5, show at the machine level how the result can be wrong. [6.7, 6.9]

A race condition occurs when several processes access and manipulate shared data concurrently and the outcome depends on the particular order in which the accesses take place. counter++ and counter-- are not atomic: each becomes three machine instructions, and the two sequences can be interleaved:

S0: producer  register1 = counter          /* register1 = 5 */
S1: producer  register1 = register1 + 1    /* register1 = 6 */
S2: consumer  register2 = counter          /* register2 = 5 */
S3: consumer  register2 = register2 - 1    /* register2 = 4 */
S4: producer  counter = register1          /* counter = 6   */
S5: consumer  counter = register2          /* counter = 4   */

The correct value is 5, but the result is 4 (or 6 if S4 and S5 are swapped): one update is lost because both processes read the old value before either stored its result. Fix: make the update a critical section executed under mutual exclusion.

X6-02All possible final values of counterCH6

counter = 5. The producer executes counter++ once and the consumer executes counter-- once, concurrently and without synchronization. Give all possible final values of counter.

4, 5 or 6.

  • 5: the two updates do not overlap (one stores before the other loads), which is the correct result.
  • 4: both load 5; the producer stores 6, then the consumer stores 4, so the increment is lost.
  • 6: both load 5; the consumer stores 4, then the producer stores 6, so the decrement is lost.

No other value is possible: each process stores (the value it loaded) ± 1, and it loads either 5 or the other process's result.

X6-03Unprotected counter in a loop: lost updatesCH6

In Lab 6 Q3, two threads each execute ++counter 5,000 times (counter = 0). If the pthread_mutex_lock() / pthread_mutex_unlock() calls are removed, is the final value still 10,000?

No. The result is non-deterministic: any value from 2 to 10,000 is possible (10,000 only if no update is lost).

  • ++counter is load, add, store; if the other thread stores in between, this thread's store overwrites (loses) the other's increments: a race condition.
  • Worst case 2: T1 loads 0 and is preempted; T2 does 4,999 increments; T1 stores 1; T2 loads 1 and is preempted; T1 does its other 4,999 increments; T2 stores 2.
  • With the mutex, ++counter is a critical section executed under mutual exclusion, so the result is always 10,000.
X6-04Race condition inside the kernelCH6

  • Processes P0 and P1 call fork() at the same time. Both read the kernel variable next_available_pid before either one updates it, so the same pid could be assigned to two different processes, unless updates of the variable are mutually exclusive.

X6-05Critical section; entry, exit, remainder sectionsCH6

What is a critical section? Describe the general structure of a process in the critical-section problem. [6.9–6.10]

A critical section is a segment of code in which a process accesses or updates shared data (changing shared variables, updating a table, writing a file), so a race condition may occur. The critical-section problem is to design a protocol such that when one process is executing in its critical section, no other process is executing in its critical section.

do {
    entry section       /* request permission to enter */
        critical section
    exit section        /* give up permission, let others in */
        remainder section
} while (true);
  • Entry section: requests permission (e.g., acquire(), wait(mutex)).
  • Exit section: releases it (e.g., release(), signal(mutex)); the remainder section is the rest of the code.
X6-06Three requirements with violation examplesCH6

State the three requirements a solution to the critical-section problem must satisfy, and give one way each can be violated. [6.11]

  1. Mutual exclusion: if process Pi​ is executing in its critical section, no other process can be executing in its critical section. Violated by: counter++ without a lock, or a lock whose test and set are not atomic.
  2. Progress: if no process is in its critical section and some processes wish to enter, the selection of the process that enters next cannot be postponed indefinitely (a process in its remainder section must not block the others). Violated by: strict alternation with turn, or a deadlock in the entry section.
  3. Bounded waiting: a bound must exist on the number of times other processes are allowed to enter their critical sections after a process has made a request to enter and before that request is granted (no starvation). Violated by: the simple test_and_set lock.

Mutual exclusion is a safety property (no wrong results); progress and bounded waiting are liveness properties. Assumption: each process executes at a nonzero speed, with no assumption about the relative speed of the processes.

X6-07Preemptive vs non-preemptive kernelsCH6

Compare preemptive and non-preemptive kernels with respect to race conditions. Why might a preemptive kernel still be preferred? [6.12]

  • Preemptive kernel: allows a process to be preempted while it is running in kernel mode, so it is not free from race conditions on kernel data, and it is increasingly difficult to design on SMP architectures.
  • Non-preemptive kernel: a kernel-mode process runs until it exits kernel mode, blocks, or voluntarily yields the CPU, so on a single processor only one process is active in the kernel at a time: it is essentially free of race conditions in kernel mode (on a multiprocessor, processes on different CPUs can still be in the kernel at the same time).
  • A preemptive kernel is still preferred because it is more responsive (no kernel-mode process can run for an arbitrarily long time while others wait) and more suitable for real-time processes.
X6-08Disabling interrupts: uniprocessor vs multiprocessorCH6

Can the critical-section problem be solved by disabling interrupts? Answer for uniprocessor and multiprocessor systems. [6.13]

  • Uniprocessor: yes. With interrupts disabled while the shared data is modified, the current code executes without being preempted or interrupted, so its instructions run in order without interleaving.
  • Multiprocessor / SMP: no, it is generally inefficient. Disabling interrupts on one CPU does not stop the other CPUs from entering their critical sections; disabling them on all CPUs requires a message to every processor, which is time-consuming, delays entry into each critical section and decreases system efficiency (it also disturbs a system clock that is updated by timer interrupts).
  • Disabling interrupts is also a privileged operation and is unsafe to give to user programs, so systems use atomic hardware instructions (test_and_set, compare_and_swap) and the locks built on them.

X6-11Peterson on modern hardware: memory barriersCH6

Why is Peterson's solution not guaranteed to work on modern computer architectures? How can it be fixed, and what are its other drawbacks?

  • To improve performance, processors and/or compilers may reorder read and write operations that have no dependencies. Peterson's entry section writes flag[i] and turn and then reads flag[j], all different variables. If the two writes are reordered, or Pi​'s read happens before its own write becomes visible to Pj​, both processes can be in their critical sections at the same time.
  • Fix: a memory barrier (memory fence), an instruction that forces all earlier loads and stores to complete and become visible to other processors before any later load or store. Alternatively, use sequentially consistent atomic operations; the Lab 6 code uses atomic_store_explicit(&flag[i], true, memory_order_seq_cst).
  • Other drawbacks: it is complex even for two processes, each thread needs different code, and it uses busy waiting (wastes CPU cycles). This is why the OS provides mutex locks, semaphores and condition variables.
X6-12Atomic hardware instructionsCH6

What does "atomic" mean? Why are atomic hardware instructions useful for synchronization, and why can't every operation simply be made atomic? [6.14]

  • Atomic = non-interruptible: the instruction (possibly several machine-level steps, e.g., read and write a word) executes as one unit that cannot be interrupted, so no race condition can occur inside it. If two such instructions run simultaneously on different cores, they are executed sequentially in some order (serialization).
  • They are the building blocks of more sophisticated tools (spinlocks, mutex locks, semaphores, atomic variables). The two common ones are test_and_set() (test a memory word and set it) and compare_and_swap() (compare a word with an expected value and, if equal, swap in a new value).
  • Not everything can be atomic: hardware instructions work on a single word / simple variable. A complex data structure (a linked list, a 1000 × 1000 matrix) cannot be updated by one atomic instruction, so locks and semaphores built on these instructions protect larger critical sections.

    *target = TRUE;

X6-16Bounded-waiting TAS: sketch proofCH6

Give a sketch proof that the bounded-waiting test_and_set() algorithm satisfies mutual exclusion, progress and bounded waiting. [6.20]

  • Mutual exclusion: Pi​ enters only if waiting[i] == false or key == false. key becomes false only by executing test_and_set(), and only the first process to execute it finds key == false; all others must wait. waiting[i] becomes false only when another process leaves its critical section, and only one waiting[j] is set to false per exit. So at most one process is in its critical section.
  • Progress: a process exiting its critical section either sets lock = false or sets waiting[j] = false; both allow a waiting process to proceed.
  • Bounded waiting: the exiting process scans waiting[] in cyclic order {i+1, i+2, …, n−1, 0, 1, …, i−1} and designates the first waiting process as the next to enter, so any waiting process enters within n − 1 turns.
X6-17Broken variants of the bounded-waiting algorithmCH6

In the bounded-waiting TAS algorithm, which requirement fails if (a) the whole exit section is just lock = false;, or (b) the exit scan always starts from index 0 instead of i + 1?

  • (a) Bounded waiting fails (mutual exclusion and progress still hold). The lock is never handed over, so the algorithm becomes the simple test_and_set spinlock: whichever process executes test_and_set first after the release wins, and a process can be overtaken indefinitely.

X6-18Atomic variables: increment() with CASCH6

What is an atomic variable? Implement increment() on an atomic integer using compare_and_swap(), and explain why a loop is needed. [6.21]

An atomic variable provides atomic (uninterruptible) updates on basic data types such as integers and Booleans; e.g., increment(&sequence) increments sequence without interruption. It is built on compare_and_swap:

void increment(atomic_int *v) {
    int temp;
    do {
        temp = *v;                       /* read the current value */
    } while (temp != compare_and_swap(v, temp, temp + 1));
}
  • CAS writes temp + 1 only if *v still equals temp, i.e., no other thread changed v since it was read. Because CAS returns the old value, the update succeeded exactly when the return value equals temp.
  • If another thread changed v in between, nothing is written and the loop retries with the new value, so no update is lost and no lock is needed. Atomic variables protect only a single variable; larger critical sections still need locks.
X6-19Mutex lock: why acquire() must be atomicCH6

Give the mutex-lock acquire() / release() code. Why must acquire() be atomic? Show what can go wrong otherwise. [6.22–6.23]

X6-20Spinlocks: when to use, not on uniprocessorsCH6

When are spinlocks preferable to blocking (sleeping) locks? Why is a spinlock a poor choice on a single-processor system? [6.22]

  • Spinlocks are preferable on multiprocessor (multicore) systems when locks are held for short times: a waiting thread spins on one processor while the lock holder runs its short critical section on another processor and releases the lock soon. No context switch is required, and a context switch may take considerable time (rule of thumb: spin if the lock is held for less than the time of two context switches).
  • On a single processor, the spinning thread occupies the only CPU, so the lock holder cannot run to release the lock until the spinner is preempted, and the spinner wastes its whole time slice. It should block (sleep) instead.
  • Likewise, if the wait may be long, a thread should block rather than spin, because busy waiting wastes CPU cycles.
X6-21Semaphore: definition, wait/signal, P and VCH6

Define a semaphore and its two operations (busy-waiting definition). What do P and V stand for? [6.24]

A semaphore S is an integer variable (a generalized lock, introduced by Dijkstra, and the main synchronization primitive of the original UNIX) that, apart from initialization, is accessed only through two standard atomic operations: wait() and signal(), originally P() (proberen, "to test") and V() (verhogen, "to increment").

wait(S) {                    signal(S) {
    while (S <= 0)               S++;
        ;  /* busy wait */   }
    S--;
}
  • wait(S): while S ≤ 0 the process waits; then it decrements S (takes a permit). signal(S): increments S (returns a permit).
  • Both must be executed atomically: no two processes may execute wait() or signal() on the same semaphore at the same time (serialization).
X6-22Why wait() and signal() must be atomicCH6

Why must wait() and signal() be executed atomically? How is this guaranteed on uniprocessor and multiprocessor systems?

  • Otherwise two processes could both test S > 0 (e.g., S = 1) before either decrements it, so both pass wait() and enter the critical section (mutual exclusion violated); S can even end at −1, or an update of S can be lost. Hence no two processes may execute wait()/signal() on the same semaphore at the same time; this is itself a critical-section problem.
  • Uniprocessor: disable interrupts while wait() and signal() execute, so their instructions cannot be interleaved.
  • Multiprocessor (SMP): disabling interrupts on every core is difficult and slow, so wait() and signal() are protected with atomic hardware instructions: compare_and_swap() or spinlocks. Busy waiting is not eliminated entirely, but it is limited to these very short code sections instead of the application's critical section.
X6-23Counting vs binary semaphore; semaphore vs mutexCH6

Distinguish counting and binary semaphores, and explain how a semaphore differs from a mutex lock. [6.25]

  • Counting semaphore: its integer value ranges over an unrestricted domain. It controls access to a resource with a finite number of instances and is initialized to the number of resources available (wait() takes an instance, signal() returns one).
  • Binary semaphore: its value is only 0 or 1. Initialized to 1, it behaves like a mutex lock, but it can also be used in other ways, e.g., initialized to 0 to enforce an execution order (S1 before S2).
  • Semaphore vs mutex lock: a mutex lock has a binary value (available or not) and is used only for mutual exclusion; a semaphore has an integer value (a generalized lock) that can also count resources and signal events / enforce order between processes. (A Pthreads mutex should be unlocked by the thread that locked it, whereas any thread may sem_post() a semaphore.)

X6-28Semaphore without busy waiting: block() and wakeup()CH6

How can a semaphore be implemented without busy waiting? Give the code and explain block() and wakeup(). [6.26–6.27]

Each semaphore has an integer value and a waiting queue (a list of processes):

typedef struct { int value; struct process *list; } semaphore;

wait(semaphore *S) {
    S->value--;
    if (S->value < 0) { add this process to S->list; block(); }
}
signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) { remove a process P from S->list; wakeup(P); }
}
  • block() suspends the calling process and places it on the semaphore's waiting queue (running → waiting) instead of spinning, so no CPU time is wasted. wakeup(P) removes P from the waiting queue and places it on the ready queue; signal() calls it only if value ≤ 0 after the increment, i.e., someone is waiting.
  • The decrement/increment is done before the value is tested (unlike the busy-waiting version), so the value can become negative, and its magnitude is the number of processes waiting on the semaphore.
  • Better than busy waiting when waits can be long; the spinning version is better only for very short waits on multiprocessors (no context switch).

P0: wait(S);  wait(Q);  ...  signal(S);  signal(Q);
P1: wait(Q);  wait(S);  ...  signal(Q);  signal(S);

X6-31Starvation (indefinite blocking) vs deadlockCH6

What is starvation in the context of semaphores, and how does it differ from deadlock? [6.28]

  • Starvation (indefinite blocking): a process may never be removed from the semaphore queue in which it is suspended, e.g., if processes are removed from the queue in LIFO (last-in, first-out) order or by priority, newer or higher-priority processes can always be chosen ahead of it.
  • Remedy: remove waiting processes in FIFO order, so every waiting process is eventually woken.
  • Deadlock: a set of processes all wait for each other and none can proceed. Starvation: the system keeps running and other processes make progress, but one process waits forever. Both are liveness failures, and a deadlock-free system can still suffer starvation.

    int my = fetch_and_add(&next_ticket, 1);   /* unique ticket */
    while (now_serving != my)
        ;                                      /* spin */
}
void release() {
    fetch_and_add(&now_serving, 1);            /* serve the next ticket */
}

XI-01read() system call: user → kernel → DMA → interrupt → returnCH3

Describe what happens, step by step, from the moment a process calls read(fd, buf, n) on a disk file until it gets the data.

  1. The program calls the C library wrapper read() (API). The wrapper puts the system-call number and parameters in registers and executes a trap (software interrupt) → mode bit set to kernel mode.
  2. The kernel's system-call handler looks up the system-call table, checks the parameters and calls the file system / device driver. If the block is not already in memory, the driver programs the disk controller for a DMA transfer (source, destination address in memory, count).
  3. The process cannot continue → state running → waiting, placed on the device's wait queue; the CPU scheduler picks another ready process (context switch: save the caller's state in its PCB, load the next one).
  4. The DMA controller transfers the whole block directly into memory without the CPU (CPU only sets up the transfer), then raises one interrupt when the block is done.
  5. The CPU saves the current context and jumps (via the interrupt vector) to the interrupt service routine, which marks the I/O complete and moves the process waiting → ready.
  6. When the scheduler dispatches the process again, the kernel copies the data into buf, sets the return value = number of bytes read (0 = EOF, −1 = error) and returns to user mode (mode bit = user).
XI-02Timer interrupt ends a time quantum (RR)CH5

What happens when the time quantum of the running process expires under round-robin scheduling?

  1. The timer (loaded by the OS with a privileged instruction) counts down and raises a timer interrupt at the end of the quantum.
  2. The CPU switches to kernel mode and jumps to the timer interrupt handler.
  3. The OS saves the running process's context (PC, registers, state) in its PCB, changes its state running → ready and puts it at the tail of the ready queue.
  4. The short-term (CPU) scheduler selects the next process (RR: the head of the ready queue).
  5. The dispatcher restores that process's context from its PCB, switches to user mode and jumps to the saved PC. The time for steps 3–5 is dispatch latency / context-switch overhead: no useful work is done, which is why q must be large relative to the switch time.
XI-03How a shell runs `ls -l > out.txt` and `ls | wc -l`CH3

Explain which system calls a shell uses to execute ls -l > out.txt and ls | wc -l.

  • ls -l > out.txt: the shell parses the line → fork() → in the child: fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644), dup2(fd, 1) (stdout now refers to the file), close(fd), execvp("ls", argv) (the redirection survives exec) → the parent (shell) calls waitpid() and then prints the next prompt. The shell's own stdout is untouched because only the child redirected.
  • ls | wc -l: the shell calls pipe(fd) before forking; child 1 does dup2(fd[1], 1) and execs ls; child 2 does dup2(fd[0], 0) and execs wc -l. Every process closes the pipe ends it does not use. The shell closes both ends (otherwise wc never gets EOF) and waits for both children.
  • Built-ins (cd, exit) run inside the shell process itself without fork: cd uses chdir(), because a child's directory change would be lost when the child exits.
XI-04Life cycle of a process through all statesCH3

Describe the life cycle of a process using the process states, naming the event that causes each transition.

  • new: created by fork(); the OS allocates a PCB and memory.
  • new → ready: admitted (long-term scheduler), placed in the ready queue.
  • ready → running: dispatched by the short-term scheduler.
  • running → ready: interrupt / time quantum expires / preempted by a higher-priority process.
  • running → waiting: requests I/O or waits for an event (e.g. wait(), read() on an empty pipe).
  • waiting → ready: I/O completion (interrupt) or the event occurs. A process never goes waiting → running directly.
  • running → terminated: calls exit() (or is killed). It stays a zombie (PCB + exit status kept) until the parent calls wait(), then its PCB is removed. Only one process is running per core at any instant.
XI-05From source file to running process (compiler, linker, loader, exec)CH2

Explain how a C source file prog.c becomes a running process.

  1. Compiler: gcc -c prog.c → relocatable object file prog.o (machine code with unresolved addresses/symbols).
  2. Linker: combines object files and libraries into one executable (e.g. ELF); static libraries are copied in, dynamically linked libraries (DLLs / shared libraries) are only referenced and linked at load or run time (saves memory and disk; one shared copy).
  3. Launch: typing ./prog makes the shell fork() a child that calls exec(). The loader brings the executable into memory (text, data, heap, stack), relocates addresses and loads needed DLLs.
  4. The OS sets up the PCB, puts the process in the ready queue, and the scheduler dispatches it; execution starts at the program's entry point, which calls main().
XI-06What happens when you press Ctrl-CCH3

What happens when the user presses Ctrl-C while a program runs in the shell, and how can a program change this?

  • The terminal driver sends the signal SIGINT (signal number 2) to the foreground process. A signal is a software notification of an event; it is asynchronous (generated outside the receiving process).
  • Default action for SIGINT: terminate the process.
  • A program can install its own signal handler with signal(SIGINT, handler) (PA1 prints a message and exits), or ignore it with signal(SIGINT, SIG_IGN). SIGKILL (9) and SIGSTOP cannot be caught or ignored.
  • In a multithreaded process the signal is delivered to one thread (or as the OS chooses: to the thread it applies to, every thread, certain threads, or a designated thread).

    for (int i = 1; i <= ITEMS; i++) {
        sem_wait(&empty);                   /* wait for a free slot   */
        pthread_mutex_lock(&mutex);
        buffer[in] = i;
        in = (in + 1) % BUF;
        pthread_mutex_unlock(&mutex);
        sem_post(&full);                    /* one more item          */
    }
    return NULL;
}

void *consumer(void *arg) {
    int sum = 0;
    for (int i = 1; i <= ITEMS; i++) {
        sem_wait(&full);                    /* wait for an item       */
        pthread_mutex_lock(&mutex);
        int item = buffer[out];
        out = (out + 1) % BUF;
        pthread_mutex_unlock(&mutex);
        sem_post(&empty);                   /* one more free slot     */
        sum += item;
    }
    printf("consumed sum = %d\n", sum);     /* 210 */
    return NULL;
}

int main(void) {
    pthread_t p, c;
    sem_init(&empty, 0, BUF);
    sem_init(&full, 0, 0);
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    sem_destroy(&empty); sem_destroy(&full);
    return 0;
}
  • Order matters: wait(empty) / wait(full) must come before locking the mutex. Locking first can deadlock (holding the mutex while blocked on a full/empty buffer).
XC-18First readers–writers (semaphores)CH6

Give a solution where many readers may read together but a writer needs exclusive access (readers have priority).

#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

sem_t rw_mutex;                             /* init 1: writers' exclusive access / held by the reader group */
sem_t mutex;                                /* init 1: protects read_count */
int read_count = 0, data = 0;

void *writer(void *arg) {
    sem_wait(&rw_mutex);
    data++;                                 /* writing */
    sem_post(&rw_mutex);
    return NULL;
}

void *reader(void *arg) {
    sem_wait(&mutex);
    read_count++;
    if (read_count == 1) sem_wait(&rw_mutex);   /* first reader locks out writers */
    sem_post(&mutex);

    printf("read %d\n", data);              /* reading (many readers at once) */

    sem_wait(&mutex);
    read_count--;
    if (read_count == 0) sem_post(&rw_mutex);   /* last reader lets writers in */
    sem_post(&mutex);
    return NULL;
}

int main(void) {
    pthread_t r[3], w;
    sem_init(&rw_mutex, 0, 1);
    sem_init(&mutex, 0, 1);
    pthread_create(&w, NULL, writer, NULL);
    for (int i = 0; i < 3; i++) pthread_create(&r[i], NULL, reader, NULL);
    pthread_join(w, NULL);
    for (int i = 0; i < 3; i++) pthread_join(r[i], NULL);
    return 0;
}
  • Writers may starve (readers keep arriving). Lab 6 wrote the same logic with two pthread_mutex_t (mutex, rw_mutex).
XC-19Zombie and orphan demosCH3

Write short programs that create (a) a zombie process and (b) an orphan process, and explain what happens.

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void) {
    /* (a) zombie: child exits, parent is alive but has not called wait() */
    if (fork() == 0) exit(0);
    sleep(1);                               /* during this time the child is a zombie (ps shows <defunct>) */

    /* (b) orphan: parent exits first, child is still running */
    if (fork() == 0) {
        sleep(2);
        printf("orphan: my parent is now %d\n", getppid());   /* re-parented to init / systemd (or a subreaper) */
        exit(0);
    }
    return 0;                               /* parent ends; the zombie from (a) is reaped by init */
}
  • Zombie = terminated, but its PCB / exit status is kept until the parent calls wait(). Orphan = parent ended without waiting, so init (systemd) adopts it and reaps it.
